### D1 · 深底 vs 浅底 = 单一真源（SSOT）

> **已有裁决**：`design/06-角色与UI/UI视觉重构方案_深色暗金国风_v1.0.md`（2026-09-13）§2.1「风格定义：深色暗金国风」+ 文首「风格定档 **A · 深色暗金国风**（主基调，全量适用）」。
> **但**：该裁决**未被执行层承认** —— 4 套视觉标准文档仍并行标"有效"，且**旧浅底文档（2026-07-24）至今未标废弃**。故本项不是"重新决策"，而是**追认既有裁决 + 冻结冲突文档**。

#### ① 现象与代价
- **四套互斥标准同时有效**，面板底色「深/浅」双向冲突：

  | 标准来源 | 面板底色 | 底色走向 | 生效期 | 现状 |
  |---|---|---|---|---|
  | `写实修仙UI可执行规范.md` v1.2 + `绘图强制规范.md` v2.0 + `UI硬性约束规范.md` v2.0 §3.6 | `宣纸 #F4EFE3` | **浅底** | 2026-07-24 | 仍标「用户终裁/已锁定」 |
  | `太玄UI主题规范.md`（`taixuan_theme.tres`） | `墨青 #1E2B28` | **深底** | 早于 09-13 | 自称「全游戏唯一视觉基准」 |
  | `UI设计令牌v1.0.md` + `组件视觉走查清单.md` | `#1B272B / #243439` | **深底异色板** | — | 待主理人审批 |
  | **`ui_theme.gd`（实际运行代码）** + `UI视觉重构方案_深色暗金国风_v1.0` | `#173B32 / #162024`（深青黛渐变） | **深底** | 2026-09-13 | **已落地 P0-1~P0-7 全部 ✅** |

- **代码事实**（`ui_theme.gd`）：
  - `COLOR_PANEL_BG = Color(0.106,0.243,0.204)`（深青灰，注释「降饱和，不要墨绿」）
  - Primitive 全为深色：`MAT_BASE_TOP #173B32` / `MAT_BASE_BOTTOM #0F2A23` / `MAT_SURFACE #1B272B`
  - `获取面板底色()` → `MAT_BASE_BOTTOM`（深）；`apply_panel_style(control, use_ink=true)`
  - 文字色为**浅色**：`COLOR_TEXT_TITLE2 #F0E6D2`、`宣纸亮` 系列 → 这是"深底浅字"的写法
- **代价**：
  1. **换肤无从谈起**：暗金/底色/文字三组值在"深底浅字"与"浅底深字"两套体系间根本对立 —— 换肤阶段一动，必须先把基底定死，否则改完返工。
  2. **83 个 UI 文件、1561 处 `Color(` 硬编码**（见 §6）无统一基底可归依，收敛目标不明。
  3. 页面易出「深底面板 + 浅底面板混排」一致性 FAIL（`03-视觉与资产治理分册 §2.6` 已明列为 FAIL 判据）。
- **上架风险**：浅底 `宣纸 #F4EFE3` 面板 + 现有浅色文字（`宣纸亮 #F0E6D2`）会直接**文字不可读**（浅字写浅底）。这意味着若选浅底，**必须同步翻转全部文字色**，不可能只改面板底。

#### ② 互斥方案
- **方案 A（推荐）· 深底为唯一 SSOT**：基底 = 深青黛/墨青；文字 = 浅色（宣纸亮）；描边 = 暗金。浅底（宣纸水墨）降级为 **P2「书院/文气」主题换肤备选**，经 Primitive 层整层替换实现，不得并行生效。
- **方案 B · 浅底为唯一 SSOT**：基底 = 宣纸 `#F4EFE3`；文字 = 墨黑 `#2E2B28`；描边 = 青黛 `#6E8F88` + 暗金。需**全量重刷 67 页 + 重出 6 张 9-patch 材质 + 全部正文/标题文字色翻转 + 重跑 64 页真实渲染验收**。
- **方案 C · 深浅双基底并存**（主页深底、弹窗/卡片浅底）：已实证是「深浅混排」FAIL 来源，且要求同一语义文字色在不同容器里取反 —— 维护成本最高，**不建议进入表决**。

#### ③ 推荐 + 理由
**推荐方案 A（深底为唯一 SSOT）**，理由全部基于盘上实证：
1. **运行态即深底**：`ui_theme.gd` 全部 Primitive/底色语义为深色，且已产出 6 张**深青黛底 + 暗金描边**的 9-patch 材质（`art/ui/patch/*.png`），`P0-1~P0-7` 阶段状态**全部 ✅**，通过 **64 页真实渲染验收**（`ACCEPT_ALL_DONE`，六计数器全 0）。
2. **浅底文档早于关键升级**：浅底标准定稿于 **2026-07-24**，早于 (a) 1080×1920 viewport 升级、(b) 2026-09-13 深色暗金国风立项。它是"历史层"，不是"现行层"。
3. **既有裁决已把浅底降级**：`UI视觉重构方案_深色暗金国风_v1.0` 明文将「B 清雅宣纸水墨」列为 **P2 主题换肤备选**、C 现代国潮弃用 —— 即浅底已被官方降级，只是没同步清理旧文档。
4. **改判代价严重不对称**：选 A 只需"冻结旧文档 + 追认"（零资产重做）；选 B 需重做材质 + 翻转全站文字色 + 全量回归，上线期不可承受。

> ⚠️ **与前次建议的冲突（如实上报）**：`03-视觉与资产治理优化分册 §1.1` 曾建议"以浅底最小包方向为默认对齐基准"。**本次基于 P0-1~P0-7 已全部落地深底的实证，改判为深底**，请老大知悉此项覆盖。

### D3 · 字号阶梯与可访问性

#### ① 现象与代价
- **代码现行阶梯（1080 基准，`ui_theme.gd`）**：
  `FONT_DISPLAY 60 / FONT_H1 48 / FONT_TITLE 45 / FONT_H2 33 / FONT_BODY 27 / FONT_VALUE 27 / FONT_DENSE 27 / FONT_AUX 21`
  折算回 480 逻辑（÷2.25）：`26.7 / 21.3 / 20 / 14.7 / 12 / 12 / 12 / 9.3`。
- **旧文档锁定**：`{22,17,18,16,15,13}`（480 基准）—— 与代码 1080 基准**不同单位口径**，直接比会误判。
- **`UI设计令牌v1.0` 主张**：`{40,32,26,24,20,18}`（整体上调）。
- **既有待裁决 R6**（`深色暗金国风方案 §9`）：`FONT_BODY=27` 折算约 **9.8dp**，低于移动端 14dp 正文标准，**倾向上调**，但须真机窄机型校准。
- **真实 viewport**：`project.godot` = **1080×1920**（`canvas_items`），开发预览窗口 720×1280（勿混为逻辑分辨率）。1080/2.25 ≈ 480 逻辑 → 真机 ≈ 411dp 宽 @2.63 DPR。
- **可访问性缺口（最要紧）**：`ACCESSIBILITY.md` 定为 **Standard 级**，要求「文本缩放 100–150% / 高对比主题 / reduce-motion / 震动开关」，但**当前无设置页承载**（`03分册 §4.2/§6` 已实证标注）→ 这些特性**无法触达用户**。
- **代价**：字号若随意上调 = 全量 breaking（挤压布局 → 破版）；可访问性设置页缺失 = 上线合规缺口。

#### ② 互斥方案
- **方案 A（推荐）· 阶梯数量级冻结 + 补可访问性**：保持 1080 基准 `45/33/27/21` 不变；**新增「高对比模式」开关**（必做）；文本缩放/reduce-motion/震动开关落**新增设置页**（reflow 非 scale）。
- **方案 B · 正文整体上调**：把正文提到 ≈14dp（≈1080 基准 37px）、标题等比放大 —— 全量重排 67 页 + 重跑 64 页验收。
- **方案 C · 采纳 `UI设计令牌v1.0` 大字号** `{40,32,26,24,20,18}` —— 全量 breaking change，须重写 `ui_theme.gd` + 全页回归。

#### ③ 推荐 + 理由
**推荐方案 A**：
1. 现阶梯的正文 `27px@1080 ≈ 10.3dp` 虽低于 14dp 理想值，但**已满足 `ACCESSIBILITY.md §2` 的硬下限**（逻辑 480 基准下正文 ≥15px → 1080 基准即 ≥33px；辅助 13px → ≥29px 量级），且 `FONT_AUX=21` 仅承载非关键信息。
2. 方案 B/C 的**唯一收益是"更舒适"，代价是全量 breaking + 上线期返工风险** —— ROI 不成立。
3. **真正的合规缺口不是字号，是"渠道"**：文本缩放/高对比/reduce-motion/震动全部依赖设置页，而设置页不存在。**把投入放到"设置页 + 高对比模式"比调字号更对症**。
4. **最小可读字号下限（明确）**：正文 **27px（1080 基准）不再下调**；辅助 21px 仅限非关键信息；关键信息禁仅用 21px 承载。
5. **高对比模式：需要**（色弱 + 低视力用户），规格引 `ACCESSIBILITY.md §7`（玄黑底 + 高亮描边、去霓虹模糊），并与「一键简化模式」共用设置页。

#### ④ 影响面
- `ui_theme.gd` 字号常量 8 个 + 全页 `add_theme_font_size_override` 散用点
- **新增**：设置弹窗（design-strategist 出 UX）+ 高对比主题（Primitive 整层切换）+ 文本缩放 reflow（engineering-lead）
- 文档：`ACCESSIBILITY.md`（补「高对比模式」落点）+ 各页 UX 规格补引分级

#### ⑤ 不可逆性
**低**。字号是常量，可逆。**若选方案 B/C 则触发全量返工**（那时不可逆），故本项推荐"不动阶梯"正是为了把不可逆面降到最小。

### D4 · 立绘重出预算

#### ① 现象与代价
- **存量规模**：`art/characters/` = **6240 文件 / 2590 MB**（占 `art/` 总量 4136 MB 的 **63%**）；含 AI 批次产出与抠底立绘。

- **方案 C · 只做后处理**：不重出，仅锐化/压缩/色调统一。

#### ③ 推荐 + 理由
**推荐方案 B（分级重出）**：
1. **方案 C 无效**：模糊根因是"纹理 < 最大显示"的结构性欠采样（`03分册 §5` 已定性），后处理无法凭空造像素；锐化只会加重"脏边"。
2. **方案 A 浪费**：6240 文件里已有大量达标资产（弟子头像 512²→显示 112.5px 达标），全量重出等于为达标品重复付费。
3. **方案 B 精准命中**：仅对"显示尺寸 > 纹理尺寸 ×1.5"的子集重出（**首要：masters 宗主立绘 + 6 套季节背景满构图版**），成本 = 全量的零头。
4. **顺序**：**先做全量后处理**（`size_limit` 按用途分级 + 非图标 `mode=0→2`）拿包体收益（目标降 ~1GB+），**再**对模糊源单列重出预算 —— 两笔投入互不冲突。
5. **重出色调须对齐 D1 基底**（深底）与 D2 金值，否则新图与既有 UI 风格分叉。

#### ④ 影响面

- 导入参数：`size_limit` 435 张 / `mode=0` 569 张 / 非 4 倍数 103 张 / `danfang_sheet`

#### ⑤ 不可逆性
**高**。重出图**不可逆**：覆盖原图后若无备份无法恢复，且出图消耗真金白银。
**强制护栏**：① 重出产物落**新目录**（`art/characters/_rerun_<date>/`），**保留原图**；② 逐张与旧图 A/B 比对（显示尺寸 ≥ 目标）后才替换；③ 替换前 `.bak`。

### D5 · `.git` 仓库瘦身

#### ① 现象与代价
- **仓库体积（实测）**：`.git` = **3363 MB**（`03分册 §5` 记为 `.git/objects` ≈ **3.28 GB**）。
- **`art/` 构成**：**9034 文件 / 4136 MB**，其中 ——
  - `.import` 2422｜`.png` 2275｜`.py` 928｜`.pyc` 919｜`.jpg` 291（115.4 MB 源图）
  - **`.bak_*` 备份 1200 个**（其中两大批：`.bak_ph6a1_20260916` **613** 个、`.bak_ph6d2_20260916` **571** 个）
  - `characters/` 6240 文件 / 2590 MB｜`icons/` 2259 文件 / 1262 MB
- **`.gitignore` 现状（已就绪）**：已含 `*.bak`、`*.bak_*`、`*.import`、`.godot/`、`Godot/`、`__pycache__/`、`.workbuddy/` 等 —— **未来不再复胖**，但**历史提交里的大二进制 blob 仍在**。
- **代价**：每次 clone / 备份 / CI 都拖 3.3 GB；仓库 = 包体之外的最大冗余负担。

#### ② 互斥方案
- **方案 A · `git gc`（保守）**：`git gc --aggressive`。
- **方案 B（推荐）· `git filter-repo` 剔历史**：保留提交历史，剔除「`art/` 中间产物 / `.bak_*` / 超大源图 / `.pyc`」的 blob。
- **方案 C · 重建仓库**：重新 `git init` + 单次提交（丢弃全部历史与 blame）。
- **方案 D · 维持现状**。

#### ③ 推荐 + 理由
**推荐方案 B（filter-repo）**，前置 = 先跑 A 探底：
1. **方案 A 治标**：`gc` 只压缩**可达**对象；对已提交的大二进制 blob **无效**（故 `.git` 仍 3.28 GB）。
2. **方案 C 不可逆且损失**：重建会**丢弃全部提交历史与 blame**（单人开发最需要的历史回溯就没了），风险最大。
3. **方案 D 持续失血**：每次备份多付 3.3 GB。
4. **方案 B 收益/风险比最优**：在**保留提交历史**前提下剔 blob，`.git` 可回落数 GB。`.gitignore` 已就绪，剔完不会再胖。
5. **硬前提（缺一不可）**：① 老大**书面批准**（改写历史 = 不可逆动作）；② **完整仓库离线备份**（另一磁盘）；③ 先在**备份副本**上演练 filter-repo；④ 剔完 `git reflog expire --expire=now --all && git gc --prune=now`。

> ⚠️ 本项**绝不在本次任务执行** —— 仅出方案与风险。改写历史须老大单独批准。

#### ④ 影响面
- 全仓库历史（所有 commit SHA 变化）
- `.gitignore` 已防护未来复胖（无需改动）
- 本地/远端引用需重新同步（单人开发以本地为准）

#### ⑤ 不可逆性
**极高**。改写历史后**无法回退到旧 SHA**（除非用备份副本还原）。
**强制节奏**：备份 → 副本演练 → 老大批准 → 正式执行 → 复跑 `git fsck` + 抽查关键文件可检出。
