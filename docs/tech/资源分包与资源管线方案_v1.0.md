# 《太玄宗门录》资源分包与资源管线方案

> **本文定位（先读这条）**
> 这是一份**施工图与决策依据**，不是执行记录。当前阶段游戏内容仍在迭代，
> 本文只做「现状量化 + 方案设计 + 分期与触发条件」，**不在本轮改任何资产或代码**。

#### 1.5.3 ⚠️ 真风险：帧动画图集与 `size_limit` 语义冲突

`art/scene_anim/danfang_sheet.png` 实测：

| 项 | 值 |
|---|---|
| 源图尺寸 | **8640 × 4242** |
| 用途 | `ui/page_building.gd:2341` 殿阁「场景英雄区」动画 |
| 图集规格 | **8 列 × 6 行 = 48 帧**，单帧 **1080 × 707** |
| 当前导入 | `size_limit=4096`、`compress/mode=2`、`mipmaps=false` |

**两个问题**：

1. **超 GPU 纹理上限**。8640 > 多数移动 GPU 的 `GL_MAX_TEXTURE_SIZE`（中低端常为 **4096 或 8192**）。
   超出时纹理可能加载失败或被强制降采样。
2. **`size_limit` 会等比例缩掉每一帧**。`size_limit=4096` 把整图降到 4096 宽 ⇒
   **单帧只剩 `4096 / 8 = 512 px`**，而单帧设计是 1080 px ⇒ 显示时被放大 2.1 倍 ⇒ **必然糊，且放大后锯齿明显**。

**根因是概念性的**：`size_limit` 作用于**整张源图的长边**，而图集是「多帧拼一张」，
所以 **图集族的定档公式与单图不同**：

```
图集：size_limit ≥ 单帧显示宽 × 2 × 列数      ← 8 列 × 1080 × 2 = 17280，远超 GPU 上限
单图：size_limit ≈ 显示长边 × 2
```

**⇒ 结论：大尺寸帧动画不能用「一张大图集」承载。** 可选路线（需实测后定）：

| 路线 | 做法 | 代价 |
|---|---|---|
| A. 拆帧文件 | 48 帧拆成 48 个独立 PNG，逐帧 `limit=1024`，用 `AnimatedTexture`/`SpriteFrames` 播放 | 文件数 +48，但显存与清晰度都可控 |
| B. 降单帧分辨率 | 明确殿阁英雄区实际显示宽（探针测），按显示宽定单帧 | 观感让步 |
| C. 分块图集 | 拆成 8 张 6 帧图集（1080×6 高），各自 `limit=2048` | 中等 |

> **前置动作**：先用 `tests/_probe_iconsize.gd` 同款方法测出「殿阁英雄区」真实显示宽，
> 再定路线。**在改之前必须 `read-before-write` 核对 `page_building.gd` 的采样方式**。

## 2. 四个痛点的归因结论

用户提出的四类问题，**横跨两个完全不同的问题域**：

| 痛点 | 实测根因 | 分包 / 高清包能否解 |
|---|---|---|
| 包体大小 | ①从未导出，真实包体未知 ②`size_limit` 无统一规格 ③部分目录漏 `.gdignore` | ✅ 能解，但**先做卫生 + 规格 ROI 更高** |
| 图标清晰度 | `size_limit` 与显示尺寸不匹配（**已解决**，见图标规范 v1.3） | ⚠️ 半能 —— 高清包只解决「高分屏」这一半 |
| 立绘 / 头像清晰度 | 同上 + 设备 DPI 上采样；部分源图分辨率不足（`masters` 显示 2806 vs 源 1216） | ✅ 能（**按需高清立绘包 = 大厂标准做法**），但**源图不足需重出，分包救不了** |
| **启动慢 ~36–53s** | **GDScript 冷启动全量编译 + 141 个顶层 preload 展开** | ❌ **完全无效，两码事** |

> **必须记住**：分包影响的是「玩家要下多少字节」，不影响「引擎要编译多少代码」。
> 启动慢的解在 §8，与本方案的资源侧手段**互不替代**。

## 3. 关键概念校正（避免后续决策踩坑）

### 3.1 「仓库 ≠ 安装包」

Godot 导出时只打包**被引用的资源**，且先做导入处理（裁剪到 `size_limit`、按平台压缩）。
所以 `art/` 的 4.1GB **不等于**安装包体。**必须真导出一次才能得到确数**（§9 P0）。

### 3.2 `size_limit` 的两种语义

| 对象 | 语义 | 陷阱 |
|---|---|---|
| 单图 | 源图长边上限 | 无 |
| **图集（多帧拼一张）** | 整图长边上限 ⇒ **单帧也被等比缩小** | **见 §1.5.3，误伤单帧** |

### 3.3 平台压缩：`compress/mode=0`（无损）在移动端代价最大

- 桌面端 UI 保 `Lossless` 是图标规范的**有意选择**（块压缩会让细线/渐变出伪影），**保持不动**。
- 但**立绘 / 背景类**（大面积渐变、照片感）改无损会让显存涨数倍：
  规范 §5.3 实测硬约束 —— `art/characters/` 全改无损 ⇒ 显存 **~240–480 MB → ~1.9 GB**，**手机端不可承受**。
- **正解两步走**：① 先按显示尺寸砍 `size_limit`（像素数降 4–7 倍）② 再改无损消除色带。两步相抵后显存持平或略降。

### 3.4 跨平台纹理变体（ASTC / ETC2 / S3TC）

`VRAM Compressed` 导入时，Godot 依据项目设置 `rendering/textures/vram_compression/import_etc2_astc`
决定是否**同时生成 ETC2 / ASTC 变体**供移动端使用。若该开关未开，Android 端会退回 S3TC 或未压缩，
**体积与显存双输**。⇒ 列为本方案 §5 的必查项（真机导出时验证）。

## 6. 方案 C：PCK 分层分包（发行层核心）

### 6.1 机制（Godot 4 原生，已验证）

```
ProjectSettings.load_resource_pack(path, replace_files = true)
```

| 参数 | 行为 | 用途 |
|---|---|---|
| `replace_files=true`（默认） | 新包的**同名路径**资源**覆盖**已有资源 | ★ **「高清包覆盖低清包」的官方机制** |
| `replace_files=false` | 不覆盖，仅新增 | 独立内容包（不破坏本体） |

- 加载后，包内资源可用标准 `res://` 路径访问，如同原本就在项目里。
- 加载顺序有意义（后加载者覆盖先加载者）⇒ **正好用来做「补丁」与「画质覆盖」**。

### 6.2 ⚠️ 必须警惕的坑：加载时机

Godot 官方明确：**若资源包加载太晚，可能看不到效果** —— 因为 `preload()` 在**脚本解析期**就锁定了资源。

> **本项目高危**：全项目有 **141 个顶层 `preload`**（`ui/game_ui.gd` 65 个、`game_state.gd` 47 个、`main.gd` 29 个）。
> 若在菜单里才加载高清包，**已被 preload 的场景不受影响**。

**⇒ 正确做法**：新建 Autoload，在其 **`_init()`**（不是 `_enter_tree()` / `_ready()`）中调用 `load_resource_pack()`，
确保**早于任何 preload 解析**。

### 6.3 建议分层设计（草案，待内容封版后细化）

| 层 | 内容 | 装载时机 | 备注 |
|---|---|---|---|
| **L0 基础包** | 引擎 + 脚本 + `config/*.csv` + 首屏 UI（`art/ui` 框架 / `art/fonts` / `art/icons/entry,hd` / `splash` / `login_bg`） | 随安装包 | **必须能进游戏** |
| **L1 核心玩法包** | 弟子立绘与头像、殿阁场景、资源图标、背景 | 首次进入对应页面时静默后台下载 | 主要体验面 |
| **L2 深层内容包** | 灵鱼 / 怪物 / 灵兽 / 皮肤 / 图鉴类 | 按内容解锁进度下载 | 长尾内容 |
| **L3 高清覆盖包** | 与 L1/L2 **同名路径**的高分辨率纹理 | 高配机型 / WiFi 下后台下载，**替换覆盖** | ★ 按需高清包 |

**分层原则**：按「**首次触达时机**」而非「美术分类」切分。
标注方法：跑引用侧扫描（`美术资源体检报告` 的 `_scan_missing_assets.py` 可复用），
产出「资源 → 引用页面 → 页面解锁条件」映射表，再据此归层。

### 6.4 主包瘦身手段

| 手段 | 说明 |
|---|---|
| `.gdignore` | 目录级排除（**已在用**，是主力） |
| 导出预设 `include_filter` / `exclude_filter` | 按 glob 排除资源（**待真导出时验证**） |
| `--export-pack` CLI | 用不同导出预设打**独立 `.pck`**（分层包的生产方式） |

> **注意**：本节所有导出侧行为**必须在真机上验证一次**再定案（项目从未导出过）。

## 7. 方案 D：Android AAB + Play Asset Delivery

| 项 | 结论 |
|---|---|
| **AAB 是否必需** | 是 —— 2021-08 起 Google Play 新应用**必须** AAB |
| **前置** | 必须启用 **Gradle 构建**（`Project → Install Android Build Template`）；Legacy 仅支持 APK |
| **install-time 分包** | **导出 AAB 时自动生效**（无需额外配置），上限 **1GB**；Google 后端按架构/密度自动分割 |
| **fast-follow / on-demand** | **无原生支持** ⇒ 需自建下载器（用 `load_resource_pack` 拉取）或第三方插件 |
| **工具链** | JDK 17 + Android SDK（platform-tools / build-tools / cmdline-tools）+ NDK；**版本须与 Godot 模板匹配** |

**⇒ 对本项目的意义**：首包控制在 **~200MB** 以内体验最佳（install-time 虽可到 1GB，但首次下载时长会劝退），
超出的立绘/高清资源走 §6 的 PCK 按需下载。

## 8. 启动慢的独立解法（★ 与分包无关，勿混）

**结论：分包/高清包对此零帮助。** 真因与解法已在 `docs/启动性能诊断_2026-09-15.md` 实测锁定：

| 阶段 | 耗时 | 根因 |
|---|---|---|
| A 引擎 init + 21 个 Autoload | **37.4 s（71%）** | **GDScript 冷启动全量重新编译**（Godot 4 无字节码持久化） |
| B `load main.tscn`（141 顶层 preload） | 10.2 s（19%） | 解析期展开依赖树 |
| E `_登录_进入` | 2.3 s | 业务逻辑 |
| F 遍历 52 二级页 | 2.4 s | 合理 |

**已验证的结论（避免重走弯路）**：
- ❌ 「顶层 preload 惰性化」在 Godot 4.7 **实测净负收益**（首页可点 50.1s → 53.4s，且把一次性成本转成 52 次操作卡顿）—— **已回滚，不要再试**。
- ✅ 已落地：开屏闪屏 + 分帧进度条，把 **47.7s 黑屏 → 0s**（观感消除，非提速）。
- ⏳ 待定：拆 `game_state.gd`（29,665 行）、Autoload 瘦身、代码标识符英文化（2.75× 理论倍率，需真实代码复验）。

## 9. 分期路线与触发条件（★ 核心）

> **当前阶段不执行任何一项**。下表是「游戏内容达标后」的施工顺序。
> 每期标注**触发条件**，避免提前做无收益的动作。

| 期 | 内容 | 触发条件 | 风险 | 收益 |
|---|---|---|---|---|
| **P0** | ① 真导出一次测真实包体（Win + Android）② 跑 §4 资源卫生 ③ 修 §1.5.3 图集超限 | **随时可做** | 极低 | 拿到确数 + 消除真风险 |
| **P1** | §5 导入规格补齐（非 icons 族定档 + 平台压缩） | 美术资产**封版**（不再批量重出图） | 低 | 包体与显存直接下降 |
| **P2** | §6 PCK 分层 + L3 按需高清包 + §7 AAB | 内容量大到首包超 ~200MB，**或**确定要上高分屏体验 | 中 | 首包可控 + 高清体验 |
| **P3** | §8 启动提速（拆 `game_state.gd` 等） | 上线前**必做**（当前 52.9s 不可接受） | 高（核心逻辑） | 玩家真实启动速度 |
| **P4** | 差量热更 / 音频分级 / 图集合并 / 预算门禁 | 有持续运营更新需求后 | 中 | 长期运营效率 |

**为什么这个顺序**：
1. P0 的「真导出」是所有后续决策的前提（现在包体是未知数）；
2. P1 依赖美术封版（否则定档白做）；
3. P2 的分包在有真实包体数据前无法定分层边界；
4. P3 与资源侧完全独立，**但必须在上线前解决**，建议与 P2 并行推进。
