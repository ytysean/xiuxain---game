## 〇、指标与分层判据（★取代「Color 计数」）

**排序判据 ＝「玩家可见缺陷 × 功能完整度」**（team-lead 定），不再以硬编码 `Color(` 数量排序。

1. **为什么不看 `Color(` 计数**：硬编码色属**视觉层**，已由 `ui_theme.gd:1459-1461` 的既定裁决收敛为**批量替换**（归 P0-4 横切批次，`分册 §2.23` 合并优化表）。逐个长尾页按色数排序会与该批次冲突、且对玩家观感的解释力低。
2. **玩家可见缺陷分级**：
   - `可见-高`：**玩家无须满足特殊条件就能看到**且明显不对 —— 占位串直曝（「完善中/敬请期待」）、中文数值/单位违规、文字 bug（重字/错字）、假信息面板。
   - `可见-中`：需特定操作/状态才浮现（某 Tab、某状态空态、某按钮点击）。
   - `仅潜在/无`：**当前不可达**（死链、死代码、不可达页）或纯代码层问题。
3. **功能完整度三级**：`完整`（真实数据读写 + 交互）/ `半成品`（有 UI 但功能空转 / 含占位）/ `占位`（纯说明或兜底页）。
4. **分层定义**：
   - **T0（本批必做）**＝ 可达 + `完整/半成品` + `可见-高` 缺陷。
   - **T1（本批应做）**＝ 可达 + `半成品`，或 `可见-中` 缺陷。
   - **T2（缓办 / 交横切）**＝ 仅视觉层问题（→P0-4）、晚期前置解锁（本阶段测试档位难达）、或经核查无可见硬缺陷。
   - **T3（专项批次）**＝ 涉**战斗红线**、只许「仅视觉层」改动的战斗相关页（**本批不做，单列专项**，见 §四）。
   - 另有 **已办**（§10/§11 已覆盖）与 **去留**（不可达页，见 §五）。

> 结论先行：用新判据重算，Step 1 的「A 级 15 页」多数**只含硬编码色**（→P0-4 横切），**真正玩家可见硬缺陷仅 2 页**（入山采撷 / 宗主管理）—— 这正是不以 Color 计数的意义。

### 3.1 道友（`ui/page_daoyou.gd`）· T1 —— ★含 `_toast` 通路核查（team-lead item 4）

**【核查结论（先给结论）】`page_daoyou.gd` 的 `_toast()` **不走玩家可见通路** ⇒ 其占位/假信息串 **当前不可达**，**列 T1（应做），非 T0**。**但**：guard 与文案须**同批**处理，否则一旦修好通路就会把「未实现」直曝给玩家。

**【实证链】**
1. `ui/page_daoyou.gd:501-503`：
   ```
   func _toast(msg: String) -> void:
       if is_instance_valid(Game) and Game.has_method("toast"):
           Game.添加提示(msg)
   ```
   guard 查的是 `Game.has_method("toast")`，调用的是 `Game.添加提示(msg)`。
2. `Game` ＝ `game_state.gd`（`project.godot:22` `Game="*res://game_state.gd"`）。**`Game` 无 `toast` 方法**（`rg 'func toast' game_state.gd` = 0 命中）⇒ `has_method("toast")` **恒 false** ⇒ 分支永不进入 ⇒ `Game.添加提示()` **永不被调用** ⇒ `_toast()` **恒为 no-op**。
3. （对照）后端通路本身**是通的**：`game_state.gd:4252 添加提示(文本)` → `:4256 提示.emit` → `ui/game_ui.gd:189-190` 连 `Game.提示` 信号 → `game_ui.gd:_toast` → `:1300-1301 ToastManager.show_tip` → 玩家可见。**断点只在 `page_daoyou` 自己的 guard 误写方法名。**
