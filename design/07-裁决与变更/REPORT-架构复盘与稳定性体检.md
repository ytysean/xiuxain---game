# 游戏架构复盘与稳定性体检报告

> 复盘目标：验证功能设计缺口、文案深化需求、综合优化方向，并重点检验"玩家实机运行会不会卡顿 / 崩溃"。
> 方法：对 7 个核心 `.gd` 全文静态走查 + 配置表/设计文档交叉比对。本环境无 Godot，结论基于代码逻辑推演，**建议关键项在 Godot 内实机复测**。

---

## 〇、一句话结论

**架构骨架健康（单例时间轴、模块解耦、无协程竞争、取数函数全部带默认值兜底），但存在 1 个真实崩溃炸弹（存档兼容）、3 个高优先性能/数据隐患（无自动存档、UI 无虚拟化、弟子无限增长），以及大量"设计已写、代码未接"的功能缺口（奇遇/装备穿戴/战斗/资源/成就/CSV 全未落地）。文案层面 200+ 模板齐备但均为" flavour 文本"，缺剧情演出、抉择分支、阵营灰度、多结局。**

**会不会崩？** 正常新档不崩；但①旧档/未来加字段的存档会崩（属性空字典）；②存档文件损坏会静默清空（无备份无版本号）。
**会不会卡？** 短时不会；但弟子数过百后"每次刷新重建全部卡片"会明显掉帧，关服一个月回来推演可能首帧卡顿 1~2 秒。

---

## 一、架构总评

### 设计层（好）
- `game_state.gd` 为 Autoload 单例「Game」，时间轴单点（§4.5 铁则六），模块用 `preload` 干净解耦。
- 无 `await`/`yield`、无动态 `load()`、`queue_free` 均配 `get_children()`，无协程竞争与节点泄漏隐患。
- `Lore` 所有 `取*` 接口用 `.get(key, 默认)` 兜底，取数越界安全。

### 代码层（缺口大）
- **48 张 config csv 全是孤儿数据**：没有任何 `.gd` 读取 CSV（`grep` 全仓无 `FileAccess` 读 csv、`csv_validator` 仅规则常量）。§4.8"全表格驱动、零硬编码"**未落地**。
- **设计已写、代码未接的系统**：奇遇触发、装备穿戴槽位、战斗/斗法、宗门大比、秘境、阵营商店、成就、新手引导、多结局——逻辑只在 `.gd` 局部或根本不存在。
- **存档无版本号、无备份、无自动存**：仅靠手动「存档」按钮。

## 二、崩溃风险清单（按严重度）

### 🔴 P0 — 必修

**C-ARCH-1：存档兼容崩溃（属性空字典）**
- 位置：`disciple.gd:309` `属性 = d.get("属性", {})` → 下游 `disciple.gd:213` `加成评分` 做 `属性["攻"]+属性["防"]+...`；`main.gd:335` 点「堂口管理」对每个成员调 `加成评分`。
- 触发：任意缺 `属性` 字段的存档（旧档 / 未来给 Disciple 加字段后未回填）。`{}["攻"]` 在 GDScript 4.x 返回 `null`，`null + int` 抛 `Invalid operands` → **硬崩**。
- 修复：① `from_dict` 缺 `属性` 时调用 `算属性()` 重建；② 或 `load_game` 对每条 `dd` 兜底 `if not dd.has("属性"): dd["属性"]={...}`。推荐①，并给 `属性` 默认值 `{"攻":0,"防":0,"血":0,"速":0}`。
- 同因：`判定职业`(line 185) 也读 `属性["攻"]` 等，同样会崩。

**C-ARCH-2：存档损坏 = 静默清空（无版本号/无备份）**
- 位置：`game_state.gd:367` `JSON.parse_string` → 损坏时 `typeof != DICTIONARY` 直接 `return`，**不报错但整档归零**；且 `load_game` 开头无 `save.json.bak` 备份。
- 触发：写档中途被杀（手机切后台/断电）、磁盘满、`user://` 权限异常。
- 修复：① `save_game` 先写 `.tmp` 再 `rename` 覆盖；② 保留上一版 `save.json.bak`；③ 存档加 `"version": N` 字段，`load_game` 版本不符走迁移而非清空；④ `parse` 失败后尝试读 `.bak`。

### 🟠 P1 — 应修

**C-ARCH-3：加权随机空字典越界**
- 位置：`item.gd:205` `return 权重.keys()[0]`、`beast.gd:162` 同式。
- 触发：当前调用方均传非空常量，安全；但**未来任一空字典传入即 index error 崩**。
- 修复：`if 权重.is_empty(): return ""` 前置守卫。

**C-ARCH-4：`main.gd` 刷新重建无防抖**
- `刷新()` 每次 `弟子变动` 都 `queue_free` 全部卡片再重建（含重算 `简介()`→`总战力()`）。`queue_free` 延迟到下一帧，若信号密集会瞬间重复建节点（不崩但闪/泄漏风险）。
- 修复：刷新加 `_刷新中` 标志去重；或改用差量更新。

### 🟡 P2 — 打磨
- `game_state.gd:101` `Lore.取堂口(d.堂口)["名称"]`：若 `d.堂口==""` 返 `{}` 取 `["名称"]` 得 `null`（不崩，仅显示空），建议 `取堂口` 对未知 key 返带默认 `"名称":"—"` 的字典。

## 三、卡顿 / 性能风险清单

**PERF-1（高）：UI 无虚拟化，刷新即全量重建**
- `main.gd:183-186` 每次刷新 `queue_free` + 重建 N 张弟子卡，每张卡 `d.简介()` 遍历 `物品` 并调 `总战力()`（再遍历 `物品`+`灵兽`）。
- 风险：N=100 尚可；**N=300+ 时单次刷新数百节点 + 重算文本，明显掉帧**；且全量塞进一个 `ScrollContainer`，无分页/虚拟列表。
- 修复（P0 性能红线配套）：① 弟子列表改为**虚拟滚动**（只建可视区卡片）；② 或分页（每页 20 人）；③ `简介()` 缓存，仅在数据变更时重算。

**PERF-2（中）：离线推演首帧阻塞**
- `main.gd:118` 在 `_ready` 同步调 `推演至现在()`。`推演` 为 O(流失日/30 × N)：`单次推演上限日=3650`→最大 ~122 次迭代 × N；每次迭代 `更新门派()`(line 257) 又 O(N) 算总战力 → 实际 ~244×N 次弟子运算。
- 风险：N=500、离线一年 ≈ 12 万次弟子运算，GDScript 下可能 **首帧卡 0.5~2 秒**（低端机更久）。
- 修复：① 推演放 `Thread` 或分步 `await`；② 启动先显「推演中…」遮罩；③ `更新门派` 复用一次 `总战力` 遍历结果（当前每月算两次）。

**PERF-3（中）：弟子数无上限，自我膨胀**
- `game_state.gd:112-117` 育英堂每月 30% 概率 +1~2 弟子；`举办测灵根` 每次 +5~20；无解散/死亡机制（`寿元` 只增不减，`年龄` 增但无死检）。N 只增不减 → 门派等级/繁荣/灵石产出全随 N 膨胀（呼应数值报告"盈余率递减但灵石净流正"）。
- 修复：① 加弟子上限（路线图 S1 已规划，建议首发就给安全上限如 120）；② 加寿元死亡/遣散；③ 离线推演按上限截断新增。

**PERF-4（低）：同步整档 JSON**
- `save_game` 全状态 `JSON.stringify` 写盘，大档（数百弟子+物品）会有一帧卡顿。配合 C-ARCH-2 的 `.tmp` 方案，大档可考虑分块/节流（非首帧关键路径，按钮触发，影响小）。

## 五、文案 / 叙事深化缺口

1. **剧情骨架化（已确认）**：代码仅 `测灵根过场`(3) + `宗门事件`(20) + 历练/奇遇模板。**创宗、首徒筑基、宗门 3 级**三大里程碑只有设计文案，无演出接口调用（过场接口 `main.gd:276` 已预留但仅测灵根用）。
2. **奇遇模板化（已确认 + 代码佐证）**：`奇遇模板` 全是"得{物}" flavour 文本，**无抉择结构**；即使接入也只当彩带，不是设计里"性格驱动双分支"。
3. **阵营人设模板化（已确认）**：`faction` 数据未接入，无灰度人设/反转剧情落地。
4. **弟子重名风险**：`姓库`(14)×`名库`(28)=392 组合，N>300 必大量重名，且无字号/道号去重（设计说性格决定道号但未实现）。
5. **世界观无强冲击节点**：`宗门事件` 偏日常播报，缺"宗门大劫""灭门之危"等强情绪事件。

## 六、综合优化建议（优先级）

### P0（首发必做，阻塞体验/数据安全）
1. **修 C-ARCH-1 崩溃**：`from_dict` 缺 `属性` 时 `算属性()` 重建 + `属性` 默认零值。→ 防旧档/迁移崩。
2. **修 C-ARCH-2 存档**：`.tmp` 原子写 + `.bak` 备份 + `version` 字段 + 损坏回退。→ 防丢档。
3. **加自动存档**：`弟子变动`/`推演结束`/`应用负责人` 后节流存盘（如每 30s 或关键事件）。→ idle 游戏基本盘。
4. **接 CSV 配置表 + 落地 `validate_all.py`**：把 `game_state` 硬编码数值（灵石+=n*5 等）改为读 `config/*.csv`；先建执行器消悬空引用（C-NEW-5）。→ 架构根因。
5. **接奇遇触发 + 装备穿戴**：最小可行——`_弟子月度事件` 按概率调 `Lore.取奇遇`；`总战力` 仅计 `穿戴位` 已装备项（加 `已穿戴` 集合）。→ 让两大系统"活"起来。
6. **UI 虚拟化 / 分页**（PERF-1）：弟子列表虚拟滚动或每页 20。→ 防百人掉帧。

### P1（首发后 1~2 版）
7. **资源体系实算**：把堂口产出 `灵气/草药/矿石` 落为真实变量，接 `config` 资源表。
8. **成就系统接入**：读 `achievement_config`，事件触发发奖（先修悬空 `reward_id`）。
9. **战斗/斗法最小闭环**：职业克制生效于弟子 vs 灵兽/事件判定；宗门大比占位。
10. **新手分步引导**：首充→首徒→首突→首奇遇 四步弹窗。
11. **弟子上限 + 寿元死亡**（PERF-3）：配合离线推演截断。

### P2（远期 / S1+）
12. **剧情演出**：三大里程碑接 `过场` 接口 + 立绘差分占位。
13. **奇遇抉择分支**：性格驱动 A/B 选项 + 连锁。
14. **阵营灰度 + 正邪路线抉择**；**多结局判定逻辑**（`GDD-结局系统.md` 先建）。
15. **推演分帧/线程**（PERF-2）；弟子重名去重（道号）。

## 七、稳定性体检结论

- **正常新档**：可玩、不崩、短时流畅。骨架设计值得肯定。
- **最大隐患**：存档兼容（C-ARCH-1/2）——这是"玩一阵子后突然崩/丢档"的典型雷，必须在首发前修。
- **最大体验债**：功能"设计全、代码空"（奇遇/装备/CSV/成就/资源），玩家实际只玩到一个"自动养成 + 文本播报"的壳。
- **性能**：百人内安全；百人以上 UI 必卡，需虚拟化。离线推演首帧在长离线+多人时可能 1~2 秒卡顿，建议分帧。

> 建议下一步：先落地 P0 的 ①崩溃修复 ②自动存档 ③CSV 接入执行器，这三项解决"能不能安心玩"的底线问题；再补奇遇/装备穿戴让系统"活"起来。
