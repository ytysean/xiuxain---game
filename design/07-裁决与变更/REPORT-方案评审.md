# 问题解决方案总览 · 评审意见

> 评审对象：`design/01-总纲/问题解决方案总览.md`（用户原始方案草案 v1.0）
> 评审结论：**框架专业、18 项问题全覆盖、优先级排期合理，可直接采纳为底稿。** 但落地前存在 7 处会埋雷的矛盾 / 缺口，分 P0 / P1 / P2 三档修正后定稿。

---

## 一、P0 级 必改项（不解决必返工）

### 1. UI 技术路线自相矛盾

- **问题本质**：“高清图集 / 矢量资源” 的美术驱动路线，与 “纯代码 Control 节点布局” 的程序驱动路线互斥。纯代码 UI 依赖节点排版实现界面，引入高清图集等于切换美术管线，两套方案并行会导致底层架构冲突，开发工时完全不可控。
- **整改方案（推荐方案①，适配独立开发现状）**：
  - 方案① 坚持纯代码 UI 路线：删除 “高清图集 / 矢量资源” 表述，UI 升级仅做**基准分辨率提升（1080×1920）+ 锚点自适应适配**；复杂看板的可视化，用 Godot 原生绘图接口实现轻量图表，不引入第三方美术插件与图集资源，保证技术栈统一，工时可控。
  - 方案② 切换混合管线：核心布局仍用 Control 节点，图标、背景、装饰元素改用图集资源；需同步评估美术资源生产工期，重新调整首发工时占比与排期。
- **落地动作**：方案中明确标注首发采用「纯代码 UI + 原生绘图」路线，删除图集相关表述，统一技术口径。

### 2. 奇遇系统裁剪与爽点需求矛盾

- **问题本质**：核心系统裁剪清单将奇遇移出首发，但新手 30 分钟爽点设计又依赖首个奇遇，内容边界前后不一致。
- **整改方案**：明确奇遇的首发定位为「探索彩蛋 + 新手爽点补充」，轻量化内置，不做独立系统：
  1. 首发不做独立的奇遇入口、图鉴体系，将 5-10 条连锁奇遇作为 “历练高阶随机事件”，嵌入历练玩法内，不单独占用系统位，符合 MVP 裁剪原则。
  2. 30 分钟节点的首个奇遇，绑定首次历练通关触发，作为新手期爽点奖励，满足正向反馈需求。
  3. 完整奇遇体系、图鉴、长剧情连锁奇遇链全部保留到 S1 赛季上线。
- **落地动作**：在核心系统清单补充标注「奇遇以历练分支事件形式轻量化内置，不做独立系统模块」，统一前后口径。

### 3. 方案为规划孤岛，缺少回填落点

- **问题本质**：所有改动仅在本方案内说明，未对应到原有 GDD 文档条目，后续开发会出现文档与方案脱节，重复踩之前 ingestion 的坑。
- **整改方案**：建立「方案改动 - 对应 GDD 文档」映射关系，所有调整同步回填原文档：
  - 宗门路线抉择 → 回填至「阵营系统 GDD」
  - 逆天改命机制 → 回填至「弟子养成 GDD」
  - 物品专属机制 → 回填至「道具与装备 GDD」
  - 多结局规则 → 回填至「结局系统 GDD」
  - 解锁规则统一 → 同步更新 C03、C10、交易系统 GDD 对应章节
- **落地动作**：方案末尾新增「文档回填清单」附录，明确每条改动对应的原文档编号、修改章节，定稿后同步更新所有关联 GDD。

## 二、P1 级 一致性整改项

### 4. 解锁术语三套并存

- **问题本质**：C03「分层解锁」、C10「双层规则（宗门总闸 + 境界细分）」、本方案「渐隐式解锁」三套术语并行，后续沟通会出现认知偏差，衍生新的规则冲突。
- **整改方案**：统一术语体系，以原文档编号为基础，本方案作为落地描述：
  1. 全局官方统一术语为**分层解锁机制**，总规则沿用 C03 定义。
  2. 商店模块的特殊规则明确为**双层解锁细则**，对应 C10 条款，属于分层解锁在商店系统的特例。
  3. 本方案中的 “渐隐式解锁”，统一改为「分层解锁（按宗门等级逐系统开放）」，显式引用 C03 文档编号，说明是原规则的落地执行方案。
- **落地动作**：全文替换术语，所有解锁规则处标注对应原文档编号，保持口径一致。

### 5. 多结局 GDD 缺口

- **问题本质**：只列了结局的产出（成就、称号等），但缺失「结局系统 GDD」作为底层支撑，判定逻辑无落地载体。
- **整改方案**：补全前置依赖，分两步落地：
  1. 首发阶段：先搭建结局系统基础框架，仅做数值累计与结局判定逻辑，暂不补全所有结局文案与分支，保证结构完整。
  2. 同步新增 `GDD-结局系统.md` 作为主文档，明确结局维度、判定公式、触发流程、奖励发放规则，本方案的多结局内容回填至该文档。
- **落地动作**：在方案依赖项中新增「结局系统 GDD」，明确其为多结局内容的前置开发项。

### 6. 性能红线口径不统一

- **问题本质**：基准测试用 100 天，压测上限写 100 年，数量级差 365 倍，红线定义模糊，无法作为验收标准。
- **整改方案**：拆分两条性能红线，分别定义场景与指标：
  1. **基准性能线（首发验收必达）**：100 名弟子，离线推演 100 天，单线程耗时≤2 秒。对应首发版本常规玩家体量，作为强制验收标准。
  2. **压测上限线（年度瓶颈预警）**：500 名弟子，离线推演 100 年，单线程耗时≤30 秒。对应后期满配玩家的极端场景，作为性能预警阈值，不做首发强制要求。
- **落地动作**：方案中分开标注两条红线的适用场景与指标，明确首发只考核基准性能线。

## 三、P2 级 打磨优化项

### 7. 气运 / 功德具体换算占比为初值

- **问题本质**：“每 100 点气运 + 3%、单维 ±20% 上限” 为经验初值，未经过实测校准，直接上线有数值崩坏风险。
- **整改方案**：规范化占位与校验机制：
  1. 所有初值统一标注 `[基准初值·待实测校准]`，明确当前为参考值，非最终定稿。
  2. 补充数值埋点与监控方案：测试阶段自动监控气运 / 功德的极值、生效占比，超出阈值自动告警；明确由数值模块负责模拟校准，测试阶段迭代调优。
- **落地动作**：在数值章节补充标注说明，新增「数值校准责任与校验机制」小节。

## 四、方案亮点保留确认

以下核心设计价值已被认可，定稿时完整保留：

1. 不可逆抉择设计（正邪道路线、逆天改命、资源总量上限），精准解决了策略 “重量不重质” 的核心问题。
2. 日常 / 事件 / 奇遇三层定位清晰，与 C10 规则无冲突，解决了功能边界重叠、玩家认知混淆的问题。
3. 数值分层校准（P0/P1/P2）的思路，与前期数值报告方向一致，兼顾了首发落地与长线迭代。
