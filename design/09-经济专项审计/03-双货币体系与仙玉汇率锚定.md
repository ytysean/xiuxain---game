# 双货币体系重构 · 与浮动汇率锚定（ECON-03）

## 〇、问题陈述（主理人原话）

> 「现在坊市里卖的全是用仙玉购买，宗门坊市应该是针对低阶弟子的，更多的应该是灵石购买的
> 物品才对。仙玉购买的高阶物品更多应该在拍卖行或者黑市。拍卖行可以用两种货币结算，
> 比如一个物品可以 1000 灵石购买，也可以 100 仙玉购买，比例具体怎么调整你来定，
> 最好是能浮动，看全服某个锚点来定。」

拆成三条可执行目标：

1. **坊市回归灵石** —— 宗门坊市面向低阶弟子，主货币必须是**灵石**。
2. **高阶物品上移** —— 仙玉计价的高阶货移到**拍卖行 / 黑市**。
3. **拍卖行双币 + 浮动汇率** —— 同一件拍品可用灵石或仙玉结算，比价由汇率决定，
   汇率**浮动**且锚定在一个全局指标上。

## 三、汇率系统设计（核心）

### 3.1 定义

```
R  = 1 仙玉兑多少灵石   （R 越大 = 灵石越不值钱）
R0 = 10                 基准（沿用 page_premium 的"十枚仙玉换N"心智）
```

### 3.2 锚定公式（三因子 + 日浮动）

```
R = clamp( R0 × f_产 × f_望 × f_浮, 6, 30 )

f_产 = clamp( 实际月产 / 标准局月产(366), 0.70, 2.00 )     ← 锚点：ECON-01 经济基线
f_望 = clamp( 1.40 - 声望 / 6000.0,        0.75, 1.40 )     ← 锚点：宗门在修真界的地位
f_浮 = 1.0 + ( 确定性随机(累计游戏日) - 0.5 ) × 0.16        ← 日浮动 ±8%
```

**每个因子的经济含义（不是拍脑袋，都有可解释性）**：

| 因子 | 升 → R 升（灵石贬值） | 为什么这样设计 |
|---|---|---|
| `f_产` | 本局月产越高，灵石越泛滥 | 灵石是**产出**货币，仙玉是**充值/稀缺**货币。灵石通胀 ⇒ 换 1 仙玉要更多灵石。这是最本质的锚。 |
| `f_望` | 声望越低，R 越高 | 声望高 = 宗门在修真界有牌面 = 与外界换汇议价能力强 ⇒ 仙玉更便宜。低阶弟子宗门换汇吃亏。 |
| `f_浮` | 每日 ±8% 内摆动 | 满足"能浮动"。用确定性 RNG ⇒ **同一天重进游戏牌价一致**（不搞"一刷新就变"的廉价感），跨日自然轮换。 |

**边界**：`clamp(R, 6, 30)` ⇒ 汇率永在 1:6 ~ 1:30 之间，最坏情况下
一件 5000 灵石的高阶货折仙玉 = `ceil(5000/6×1.15) ≈ 959 仙玉`，
最好情况 = `ceil(5000/30×1.15) ≈ 192 仙玉`。两端都在项目现有仙玉价格带
（30~1000）的合理区间内，**不会出现"1 仙玉买光整店"的破盘**。

### 3.3 实现落点（新增，不改既有消费点）

```
game_state.gd
  var 汇率_日缓存: float = 0.0
  var 汇率_缓存日: int = -1
  func 当前汇率() -> float            # 带日缓存的 R，O(1)
  func 汇率牌价文案() -> String        # 「今日牌价：1 仙玉 ≈ %d 灵石（%s）」
  func 灵石折仙玉(灵石价: int) -> int   # ceil(灵石价 / R × 1.15)
  func 仙玉折灵石(仙玉价: int) -> int   # floor(仙玉价 × R / 1.15)

config/经济基线.csv（追加 4 行，提交即锁；闸门 Layer A 自动守 ±15%）
  仙玉基准汇率,10,ECON-03 §3.1 基准 R0
  汇率下限,6,ECON-03 §3.2 clamp 下界
  汇率上限,30,ECON-03 §3.2 clamp 上界
  仙玉结算溢价,1.15,ECON-03 §4.2 用仙玉结算需多付的比例
```

> **为什么不塞进 `经济阀门.csv`**：该表 4 个旋钮是"产出/消耗纠偏"的
> **运行时倍率**（由 `economy_balance.gd` 钳制），语义与"汇率常数"不同。
> 汇率常量属**基线锚**，归 `经济基线.csv`，与闸门 Layer A 的 ±15% 系数守一致。

### 3.4 预留全服注入点（未来接云端时零重构）

```gdscript
## 若未来接入云端全服行情，只需覆写此函数返回服务端 R，
## 本地方案的公式自动降级为"离线兜底"。
func 当前汇率() -> float:
    var 远端: float = _汇率_取自云端()      # 现在恒返回 0.0（未接入）
```

## 四、拍卖行双币结算设计

### 4.1 拍品数据（新增字段，**不改既有字段语义**）

```
拍品 = {
    底价: 5000,                 # 既有字段：灵石底价（保持不变，闸门/存档零影响）
    底价仙玉: 0,                # 新增：派生值，= 灵石折仙玉(底价)；0 表示按当日实时算
    ...
}
```

**派生不落盘** —— `底价仙玉` 每次读取时用 `灵石折仙玉(底价)` 现算。
理由：汇率每天变，落盘会把"当日报价"写死进存档，跨日读档后与 UI 牌价不一致，
反而制造"显示价 ≠ 实扣价"的老毛病（本项目历史上已经踩过这个坑）。

### 4.2 出价与比价

| 环节 | 规则 |
|---|---|
| 出价货币 | 玩家自选（UI 双按钮或货币切换） |
| 仙玉结算溢价 | 付仙玉须多付 **15%**（`仙玉价 = ceil(灵石价 / R × 1.15)`）—— 理由是仙玉是硬通货，用硬通货买流通货物理应不划算，**主动引导玩家用灵石参与中低端竞拍、只在抢高阶货时动用仙玉** |
| 同场比价 | 统一折算为 **灵石等价** 后比较：`等价 = 出价 × (1 if 灵石 else R)`；最高等价者得 |
| 冻结 | 灵石出价冻结灵石，仙玉出价冻结仙玉（**分池冻结，不互相换算**，避免汇率日变动导致冻结额漂移） |
| 成交扣款 | 按出价时的货币原币扣，不回溯汇率 |

### 4.3 UI 呈现（复用现有组件，不新增控件类型）

拍品卡底部改一行即可：

```
底价  5000 灵石
   或  435 仙玉           ← 新增一行，用现有 UITheme 的辅助文本样式
今日牌价 1 仙玉 ≈ 11.5 灵石（页头常驻一处，全页共用）
```

**只加文字与一个货币切换钮**，不引入新卡片样式 ⇒ 符合 UI 三连规范
（复用现有组件/颜色、禁自定义图标与硬编码颜色）。

## 五、坊市页信息架构调整（对应病灶一）

### 5.1 目标结构

```
宗门坊市（page_shop）
  ├─ 灵材   ← 默认 Tab，纯灵石（faction_shop.csv，声望门槛）
  ├─ 收购
  └─ 仙缘阁 → 独立页 or 折叠为末位 Tab（纯仙玉）
```

**三个动作**：
1. `_当前分类` 的默认值从「推荐」（仙玉）改为**灵石商品 Tab**。
2. 「今日特供」整体移入**仙缘阁**语义区（它本就是仙玉商品），不再出现在坊市首屏。
3. `page_shop` 顶部的标题若含"坊市"，则仙缘阁区域必须**显式标为「仙缘阁」**，
   让玩家一眼分清两个货币体系。

### 5.2 与"今日特供"的关系

本日已把「今日特供」数据源从 `faction_shop`（阵营声望商店，语义错位）
换成 `XianyuShop`（仙缘阁商品库）+「仙玉刷新」。**这一步方向正确**，
但结论是：**它属于仙缘阁，不属于坊市** ⇒ 随第 2 个动作一起迁移。

### 5.3 顺带发现：**灵石商品卡片没有图标**（本轮探针实证）

坊市探针命中「收购」Tab 时，4 张灵石商品卡的 `Icon` 节点**全部不存在**
（`find_child("Icon")` 返回 null，卡片回退到"首字"占位）：

```
Card_shop_modao_004   名「魔道传承玉简」 价「5500 灵石」 图标min=«缺»
```

**根因**（`ui/page_shop.gd:685-688`）：

```gdscript
# ui/page_shop.gd:685-687（现盘代码）
var icon_path: String = str(商品.get("icon", ""))
var tex: Texture2D = (load(icon_path) as Texture2D) if icon_path != "" else null
if tex != null:                      # ← 只有 tex 非空才创建 Icon 节点
    var icon := TextureRect.new()
```

> 注：该行"空路径"虽有 `if icon_path != ""` 守卫，但**任一路径不存在时 `load()` 仍会报
> `Resource file not found: res://...`**（探针实测）。P0-C 改走 `解析图标()` 一并收敛。

而 `config/faction_shop.csv` 的列是
`item_id,faction,faction_id,item_name,item_type,unlock_reputation,price,description`
—— **根本没有 `icon` 列** ⇒ `icon_path` 恒 `""` ⇒ `Icon` 节点永不创建。

> 对比：仙缘阁商品（`XianyuShop`）自带 `icon` 字段，同屏的「客卿」Tab 三张卡
> 图标实测均为 `(104.0, 104.0)` —— 尺寸改造本身是生效的，
> **只有灵石商品这条链路缺图标数据**。

**处置裁决（2026-09-15）**：**不给 CSV 加 `icon` 列，改走「约定式寻址」**。

三条候选方案对比：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 给 CSV 加 `icon` 列 | 20 行逐条填全路径 | ★ 新增商品时必须**手工补一列**，漏填就静默掉占位；且要改 CSV 表头（其它消费者也要复核） |
| B. 按 `item_type` + `faction_id` 推导映射 | 维护 `5×5` 映射表 | 同类型商品**共用一张图**（3 件功法长得一样）⇒ 货架廉价感反而更强；映射表还要人维护 |
| **C. 约定式寻址（选定）** | 文件名 = `item_id`，落 `art/icons/shop/` | 零映射表、零 CSV 改动、**新增商品"丢图即有图"** |

**落地三点**（P0-C）：

1. `UITheme.load_hd_icon()` 增 `shop_` 前缀分支 → `res://art/icons/shop/`。
2. `UITheme.解析图标(v)` 新增 —— 兼容"`res://` 全路径"（仙缘阁现状）与"裸 stem"（坊市新方式），
   并内置 `ResourceLoader.exists()` 保护 ⇒ **顺带修掉 `page_shop.gd` 的 `load("")` 报错**。
3. `_坊市表()` 补 `icon` 别名键 = `item_id` —— 与已补的 `shop_id`/`price_lingjing` **同一处**，
   维持"单点修复、全消费点自动受益"的心智一致性。

**出图移交外批次**（主理人：*"图标我让豆包生成"*）——
规格书：`design/06-角色与UI/坊市商品图标出图规格-外批次_2026-09-15.md`（含 20 件逐件画面描述）。
因 `ResourceLoader.exists()` 已做保护，**出图与通路建设完全并行、互不阻塞**：
图没到显示"首字"占位，图落盘即自动生效，**不需要再改一行代码**。
