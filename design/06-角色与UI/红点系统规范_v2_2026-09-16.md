## 一、v1 的四个真问题（实测，非观感臆断）

| # | 问题 | 根因（代码实证） | 后果 |
|---|---|---|---|
| 1 | **两套实现并存** | `ui_theme.gd::make_red_dot*`（首页/主界面/弟子详情/任务/纪事辅助在用）与 `ui/red_dot_badge.gd`（建筑升级页 / 纪事页在用）**各写一份配色**：前者 `Color(0.9,0.2,0.2)` + **白描边**，后者同样红但尺寸逻辑不同 | 同屏两种红点观感不一致，规范无法收口 |

## 二、v2 规范

### 2.1 形态

| 类型 | 语义 | 几何 |
|---|---|---|
| **圆点**（dot） | 有未查看内容，数量无意义 | 正圆，直径 = 调用方给定（默认 16） |
| **数字胶囊**（number） | 有 N 件待处理 | 高 = 调用方给定（默认 20）；宽 = `max(高, 高×0.62×位数 + 高×0.52)`，即**两端半圆的胶囊**；单位数时退化为正圆 |
| **上限** | — | `> 99` 显示 `99+` |

### 2.2 配色（唯一定义处：`ui_theme.gd`）

| 常量 | 值 | 用途 |
|---|---|---|
| `RED_DOT_COLOR` | `(0.90, 0.20, 0.20, 1.0)` | 主红底 |
| `RED_DOT_BORDER` | `(0.16, 0.05, 0.06, 0.92)` | **深玄描边**（替代 v1 的纯白）——深底不脏、亮底不糊 |
| `RED_DOT_GLOW` | `(0.04, 0.02, 0.02, 0.45)` | 外发光（`shadow_size ≈ 0.16×直径`）——把红点从亮色山水背景上"抬"起来 |

数字文字：白色 + **同色深描边**（`outline_size ≈ 0.14×高`）——红底小字号白字无描边必糊。

### 2.3 落点

- **统一规则**：红点中心落在宿主（或宿主图标）**右上 45° 外沿**，且约 **60% 压进宿主外接矩形内**、40% 外溢"咬"住边角。
- 首页入口：偏移 = `ENTRY_SIZE × 0.37`（图标半径 0.5×66.2 的 45° 外沿在 0.354 倍处；旧值 0.42 会飘出圆环）。
- 首页 dock：`x = QUICK_BTN_W×0.5 + QUICK_ICON_SIZE×0.35`，`y = QUICK_BTN_H×0.42 − QUICK_ICON_SIZE×0.35`。
- 通用控件（`red_dot_badge`）：`offset_right = sz.x×0.4; offset_left = offset_right − sz.x`（宽 = sz.x），纵向同理。

### 2.4 动效

- 出现：`scale 0 → 1`，`TRANS_BACK` / `EASE_OUT`，0.2s（`UITheme.animate_red_dot_appear`）
- 消失：`scale 1 → 0`（`UITheme.animate_red_dot_disappear`）
- 刷新路径**必须走这两个函数**，禁直接 `visible = true/false`（否则无入场动效，突现很廉价）。

### 2.5 收敛原则（防"廉价页游感"）

1. **一个入口只挂一个红点**，父级不做数字累加，只做"存在性冒泡"。
2. 红点必须**可清除**：点进对应页即消；不做"点不掉的红点"。
3. 同一屏红点数量宜 ≤3；超过说明功能设计有问题，应由信息架构解决而不是加更多红点。

## 五、v2 收尾（2026-09-16 下半场 · 已实测验收）

### 5.1 几何的最终口径：**一律按实际像素尺寸自适应**

`StyleBoxFlat` 的 `corner_radius / border_width / shadow_size` 是**节点单位**，
而首页 `_place(c,x,y,w,h)` 传入的是**设计逻辑值**（内部 ×`UI_SCALE`）。
两者混用 ⇒ 圆角只有应有值的 `1/2.25`，红点在屏上是**圆角方块**。
故 `make_red_dot` / `make_red_dot_number` 内部改为闭包 `同步()`，每次按 `dot.size` 重算，
并**同时**连接 `resized` 与 `tree_entered`：

- `resized`：尺寸变化时重算；
- `tree_entered`：因为 `_place()` 是在 `add_child` **之前**设 size 的，
  未入树时 `resized` **不会触发** ⇒ 只连 `resized` 会停在初值尺寸上，同样退化成圆角方块。

### 5.2 数字角标的胶囊宽度公式（单位数必须正圆）

```
宽 = max(高, 高 × (0.62 × 位数 + 0.38))
```

- 位数 = 1 ⇒ 宽 = 高 ⇒ **正圆**（旧式 `+0.52` 给出 1.14 倍 ⇒ 单个数字角标渲染成椭圆，实机复现）。
- 位数 = 2 ⇒ 宽 ≈ 1.62 高，标准两位数胶囊。
- `设置红点数量(dot, n)` 就地改数量并重算宽度；`dot.size` 与 `_place()` 同口径（节点单位）。

### 5.3 顶栏未读角标（S56 消息按钮）

| 项 | 定稿 |
|---|---|
| 图标 | `entry_feifuchuanxin_36`（「飞符传讯」，与传送讯中心同语义、同美术体系）。旧实现是系统 emoji `📜`，随机型字体变化且与金质图标体系脱节 |
| 角标 | `make_red_dot_number(0, 16)`，高 16 逻辑（≈12dp） |
| 落点 | 圆心 = 图标 45° 外沿（`R/√2 ≈ 0.707R`）再外扩 1 逻辑 ⇒ 半压在图标右上角 |
| 锚定 | **右缘锚定**：位数 1→2 时向左生长，右缘不动（屏宽 480、按钮右缘 476，余量极窄） |
| 动画顺序 | 先 `设置红点数量` → 再定落点 → **最后**播入场（动画需按最终尺寸算轴心） |

### 5.4 动效轴心

`UITheme.animate_red_dot_appear / disappear` 必须先 `dot.pivot_offset = dot.size * 0.5`。
`Control.scale` 默认绕**左上角**缩放，不设轴心会让角标看起来「从自己左上角往右下平铺弹出」。

### 5.5 实测证据（`tests/_probe_reddot` + 像素连通域）

- 顶栏角标红核 **18×18**（w == h ⇒ 正圆），数字白字带深描边，外圈柔光可见。
- 首页 dock 红点 **13×13**（w == h ⇒ 正圆）。
- 探针实测：`visible=true scale=(1,1) pos=(1035.43, 40.07) size=(36,36) txt=2 pivot=(18,18)`。

> 判定「圆 vs 圆角方块」只能用**像素连通域**：节点的 `size` 是圆的**外接方框**，
> 无论圆角多小，用 `size` 都判不出来。

### 5.6 验收 harness 的两个前置修复（否则截图永远拍不到角标）

1. `_settle(n)` 补**墙钟时间下限 260ms**（帧数 ≠ 时间，动效是时间制 tween）。
2. 开页前**强制种 2 条未读**：harness 每轮都会走到「传讯中心」→ 标记全部已读 → 存档，
   于是下一轮首页未读数恒为 0，角标整轮不出现 ⇒ 截图关卡对这块失去回归能力。

### 6.3 「一眼就很好点」的四个工程条件

| 条件 | 实现 | 为什么这是「好点」的关键 |
|---|---|---|
| **形态按数据分档** | 父级 `count > 0` → 数字角标；父级仅状态（`count == 0` 而 `是否显示 == true`）→ 圆点 | 与微信一致：Tab 用圆点（只表示"有新"）、列表用数字（有明确数量）。**不硬编，由数据形态决定** —— 父级自身 count 恒为 0 只做聚合，这个映射天然成立 |
| **点击穿透** | 角标 `mouse_filter = IGNORE`；Tab 热区是整块 `Hitbox_*`（88×80 逻辑） | 角标只是**标记**，点的是整个 Tab。角标若吃点击，手指落在角标上会"点了没反应"—— 这正是「不好点」的典型症状 |
| **永不被遮挡** | 角标建在 `Hitbox_*` **之后**（Godot 中后 add 者在上） | 否则被热区面板盖住：看得见、点不着 |
| **右贴角锚点** | 数字**右缘**与圆点右缘对齐、向左扩 | 位数 1→2 时锚点不跳，视觉才稳（与顶栏未读角标同口径） |
| **弱信号隔离** | `注册父子(父, 子, 参与计数)`：传 `false` 的子级只贡献「有无」，不进父级数字汇总 | **改完在实机截图里才发现**：`弟子_装备` 的判据是「装备槽 < 9」且逐弟子计一次 ⇒ 9 名弟子全空装 ⇒ Tab 显示虚高的 **9**，而真实可突破人数为 0。红点一旦虚高就失去可信度（"亮着 9，点进去无事可做"）。隔离后：有数量型待办 → 数字；仅弱信号 → 自动降级圆点 |

### 6.6 沉淀的通用教训

1. **`continue` / `return` / `break` 之后仍多一层缩进的代码块 = 语法合法但永不执行。**
   这是 gdtoolkit / 类型扫描 / 缩进扫描 / 全部闸门的**共同盲区**，本轮是第二次踩到
   （首次是 `game_state.gd::_读经济基线()`）。**读函数体 + 探针实测是唯一手段**，
   尤其是「写了 `visible` 却没生效」「数组总被清空」这类"看起来不该发生"的症状。
2. **状态算完了 ≠ 界面显示了。** `red_dot_init` 算式再对，没人承接就等于零。
   审计红点必须两头看：**算得对不对（数据）** + **有没有节点接（渲染）**。
3. **不要给"发光"配暗色。** `shadow_color` 用近黑只会得到一圈脏灰；在深色面板上更是完全隐形。
   这类"看着像加了效果、实际是负收益"的修饰最难发现 —— 因为它不报错。

## 七、v3.1 判据铁则：红点 = 宗主待裁决队列（2026-09-16 · 已实测验收）

> 老大原话：「弟子装备无需提醒，因为我和其他游戏不同的地方就在于**弟子完全由 AI 内驱行为逻辑**，
> 装备都是自己装备，道具也是自己使用。」

被推翻的是**判据本身**。v3 之前的红点表是按「常规手游」习惯列的：可突破 → 红点、空装备槽 → 红点。
但本项目的核心差异点恰恰是**门下弟子全员内驱** —— 给弟子挂待办，等于**逼玩家去抢弟子自己会做的事**，
玩家点进去发现"无事可做"，红点随即失去可信度（"点不掉的红点"）。

### 7.1 判据（一句话）

> **「这件事宗主不做，弟子 AI 会不会替自己做？」—— 会自决的，一律不产生红点。**

红点只承载**宗主待裁决队列**，不承载「弟子进度提醒」。

### 7.2 代码实证（判据不是设计口号，是既成事实）

| 行为 | 实现位置 | 是否需宗主 |
|---|---|---|
| 弟子获得物品 → 自动穿戴（更优则替换） | `disciple.gd:2255 获得物品` → `:2257/:2260 自动穿戴` | ✗ 全自动 |
| 私库自动穿戴 + 自动服用丹药 | `disciple.gd:2295 私库自动使用` → `:2298/:2299`（月度推演 `game_state.gd:14055` 调用） | ✗ 全自动 |
| 自行突破（性格 + 寿元 + 连败压力驱动阈值） | `disciple.gd:3066 AI决定是否突破` | ✗ 自决 |
| 主动服药冲关（**直接从宗门库房取丹**） | `disciple.gd:3093 AI主动准备突破`（`:3106` 遍历 `Game.宗门库房`） | ✗ 自取 |
| 主动申请洞府 / 寻机缘 | `disciple.gd:3127 AI申请洞府` / `:3137 AI主动寻机缘` | ✗ 发起侧自决（批复才需宗主） |
| 竞拍中自行寄售重复装备 | `auction_system.gd:1010 _弟子AI竞拍决策_S34`（`:1091-1098` 判断"已有更优同槽即寄售"） | ✗ 自决 |
| 护法 / 洞府 / 请誓 / 待抉择 | `game_state.gd:1169 弟子护法传讯` / `:1185 弟子洞府传讯` / `:1332 誓约待批` / `:324 待抉择` | **✓ 宗主落笔** |

### 7.3 四类执行者 → 两条通道

| 执行者 | 典型行为 | 通道 |
|---|---|---|
| ① 司职弟子自动 | 月课 / 升迁 / 施药 / 领用 | 纪事（告知） |
| ② 弟子自身 AI | **穿装备 / 服丹药 / 突破 / 寻机缘** | 纪事 / 属性面板（告知）—— **禁红点** |
| ③ 条件触发·因缘 | 护法 / 洞府 / 请誓 请示 | **传讯·待批 → 红点** |
| ④ 宗主不可代劳 | 任命 / 驱逐 / 请誓裁夺 / 定突破方针 / 洗池付费 | **红点** |

关键分界：② 与 ③ 表面都是"弟子做了个动作"，但 ② 的结论弟子自己就出了，③ 的结论**必须宗主落笔**。
判据落实在 ③。

### 7.8 一条待老大拍板的设计项

`ui/disciple_detail_page.gd:2266` 有「一键最优穿戴」按钮（宗主替弟子穿装）。
按铁则，它**不产生红点**（已确认），但它本身是否该保留，取决于：
**宗主是"决定把哪件装备分给谁"（分配权，合理），还是"替弟子穿"（执行权，与内驱设定冲突）？**
若为前者，建议把按钮语义改为「配予该弟子」（写入背包即触发其 `自动穿戴`），与弟子自决不矛盾。
