### 1.3 为什么帧率不能判定 —— 三条硬理由（不是"保守"，是"口径不成立"）

1. **测量设备是桌面独显，不是手机。** 基线日志首行：`Vulkan 1.4.348 - Forward+ - Using Device #0: Intel - Intel(R) Arc(TM) B580 Graphics`（`_perf3_ok.txt`）。桌面 Forward+ 的 FPS 与移动端 TBDR/移动 GPU 之间**没有可用的换算关系**。
2. **渲染路径未对移动端做过任何设定。** `project.godot:59-62` 的 `[rendering]` 段**只有两行 2D 吸附**（`2d/snap_2d_transforms_to_pixel` / `snap_2d_vertices_to_pixel`），**没有 `renderer/rendering_method`、没有 `.mobile` 覆盖、没有 `vram_compression/import_etc2_astc`**。项目**从未导出过**（无 `export_presets.cfg`，`docs/tech/资源分包与资源管线方案_v1.0.md:52`、`:459`）⇒ 移动端会走哪条渲染路径、纹理会不会退回未压缩，**都是未知数**（该 doc `:235-239` 已把 `import_etc2_astc` 列为"真机导出时必查项"）。 *(知识缺口：Godot 4.7 `rendering_method.mobile` 的默认取值我未在官方文档核实，不臆断；真机导出时实测为准。)*
3. **同一份基线内部就自相矛盾，不能做任何归因。** perf3 与 perf4 **不是可比负载**：

   | 指标 | perf3 | perf4 | 差 |
   |---|---|---|---|
   | FPS（3 轮） | 80 / 70 / 70 | **88 / 37 / 50** | 抖动 37–88，**无单调性** |
   | DrawCall | 141 | 124 | −17 |
   | texmem | 77.4MB **恒定** | 86.2MB **恒定** | +8.8MB |
   | OBJECT_COUNT | 16364→16380 | 12485→12503 | −3900 |
   | ORPHAN_NODE | 5868→5876 | 4068→4077 | −1795 |
   | 功绩堂构建 | 588ms | **116ms** | −472ms ✅ |
   | 退出 ObjectDB 泄漏 | 13901 | **1436** ✅ | 泄漏已修 |

   perf4 是"泄漏已修 + 功绩堂已优化"的更晚版本，**但它的 FPS 反而更差、抖动更大**。
   在**没有受控对照、没有 p99 帧时间、且测量点落在 12 页重构建之后**的情况下，
   "FPS 70–80 达标 / FPS 37 崩了"**两个结论都推不出来**。
   **⇒ 这组帧率数据的正确用法是"存疑待重测"，不是"判定"。**

### 1.4 剩余性能风险点（按"是否需要立刻动手"排序）

#### 风险 1 · 启动耗时构成：**主项既未修复、也未被正确测量**（P0）

| 阶段 | 耗时 | 占比 | 根因 | 出处 |
|---|---|---|---|---|
| A 引擎 init + 21 Autoload | **37.4 s** | 71% | **GDScript 冷启动全量重新编译**（Godot 4 无字节码持久化；本项目 253 个 `.gd` / 154,786 行 / `game_state.gd` 单文件 29,665 行 = 1.37MB） | `docs/启动性能诊断_2026-09-15.md:36-58`、`docs/tech/资源分包与资源管线方案_v1.0.md:188-194` |
| B `load main.tscn`（141 个顶层 preload 展开） | **10.2 s** | 19% | `ui/game_ui.gd` 65 + `game_state.gd` 47 + `main.gd` 29 个**顶层 preload 在解析期就全量展开** | 同上 `:59-68` |
| E `_登录_进入` | 2.3 s | 4% | 业务逻辑，**仍是同步卡顿**（未改协程） | `:377`、`docs/启动性能诊断:312` |
| 合计到首页可点 | **52.9 s**（两次 52.052 / 52.879） | — | — | `:30` |

**必须记住的三件事**（避免重走弯路）：
- ✅ **已落地**：开屏闪屏 + 分帧进度条，黑屏 47.7s → 0s（观感消除，**非提速**）→ `docs/启动性能诊断_2026-09-15.md:247-281`。
- ❌ **已证伪**：**不要**再试"顶层 preload 惰性化" —— 实测净负收益（首页可点 50.1s→53.4s，并把一次性成本转成 52 次操作卡顿），已回滚并归档 `game_ui_lazy_REJECTED.gd`（`:169-196`）。
- ⚠️ **合成对照实验整条作废**（E/F 组数据自相矛盾，负载污染）⇒ **中文标识符 2.75× / 单文件 2.1× 两个倍率不得作为决策依据**（`:305-311`）。
- ⚠️ **`ui_theme.gd:1572 / 1597` 的 shader bug 仍在**（GLSL `fragment()` 内 `return`）⇒ **玩家每次启动都报 SHADER ERROR 且底板材质失效**（`:80-92`、`:380`）。

#### 风险 3 · 常驻纹理峰值：**"无上限"是设计，且峰值从未被测**（P1）

- **证据（这是设计而非 bug）**：`ui/game_ui.gd:891-901` 把访问过的二级页实例**存进 `_sub_pages` 字典不复用即不释放**；`:985-994` 的注释明写"页面缓存是刻意设计（切页只 remove_child、实例留字典复用），故运行时 `OBJECT_ORPHAN_NODE_COUNT` 恒高并非泄漏"；释放只发生在 `_exit_tree()`。
- **后果**：`ENTRY_SUB_PAGES` 共 **52 个键**（`ui/game_ui.gd:92-147`）+ 5 个 Tab + 详情/商店/世界地图等，**全部访问一遍后全部常驻**，无 LRU、无上限。
- **探针只走了 12 页**（`_probe_perf.gd:10-14`）⇒ 77.4MB 这个"恒定值"**只说明"12 页不涨"，不说明 52 页的天花板**。
- **量级线索**：`art/` 4,117.2 MB / 2,265 张源 PNG，其中 513–1024 有 1,526 张、1025–2048 有 446 张；纹理导入规格里 `size_limit=0`（不限尺寸）有 **1,241 张**（`docs/tech/资源分包与资源管线方案_v1.0.md:120-133`、`:446-460`）。**这些数不能直接换算成峰值**，但足以说明"峰值风险真实的存在"。
- `ui_full_accept` 已经能跑 64 页真实渲染（`ui_acceptance_report.md` 同目录有 `ISSUES n=0 · SHOTS n=64`），**但它的报告不落显存峰值** ⇒ 需要补打点。

## 2.2 缺口 ②：符词条战力**无子帽、无全局封顶**（经济增益上限红线的真实缺口）

### 2.2.1 病灶

| 位置 | 事实 |
|---|---|
| `game_state.gd:8360-8364` | `护身符战力加成(弟子)` 返回 `符词条聚合(...).get("战力", 0.0)` —— **裸 float** |
| `game_state.gd:8326-8342` | `符词条聚合()` 只是把 `数值` **直接相加**，**无 clamp、无子帽、无条数上限** |
| `disciple.gd:1555-1557` | `base += float(Game.护身符战力加成(self))` —— 加在 **`base`（乘性主体之前）**，因此会**被后面 15 个乘区全部放大** |

### 2.2.2 对照组：装备词缀是**有帽**的 —— 说明这不是"项目没规范"，而是"符词条漏了规范"

```
disciple.gd:1934-1943  # 聚合通用增益()
    装备词缀池 += float(a.get("数值", 0)) / 100.0
    var 装备子帽: float = clamp(装备词缀池, 0.0, 0.08)   # 单源子帽 ≤8%
    通用增益总和 = 装备子帽 (+ 付费增益值)
    return _clamp_soft(通用增益总和, 0.25, 0.30, 0.2)     # 软 25% / 硬 30%，溢出按 20% 衰减
```
参照 `ADR-001-equip-wearing.md:65`（决策 D3 的 `通用增益` 定义）。

⇒ **同一个项目里：装备词缀 ≤8% 子帽 + 25/30% 全局帽；符词条完全裸奔。**
这就是任务书说的"经济增益上限红线未生效"的**唯一实体缺口**。

### 2.2.3 改法

| 步骤 | 改动 | 风险 |
|---|---|---|
| **T1** | 给 `符词条聚合()` 的 `战力` 一类加**单源子帽**（建议与装备同量级；具体值需经济专项定档） | 低（纯 clamp） |
| **T2** | 把护身符贡献**并入 `聚合通用增益()` 的统一池**（与装备词缀/付费增益共享 25/30% 帽），而不是加在 `base` | **中**：会**降低**现有玩家的战力读数 ⇒ 必须有"改前/改后差值"证据 + 逐档抽查 |
| **T3** | 在 `audit`/闸门侧加一条**静态断言**：`护身符战力加成` 的返回值必须经过 clamp（可用"函数体内出现 `clamp`/`_clamp_soft`"做文本断言，与 `check_resource_redline.py` C 层同一手法） | 低 |

> **注意**：T2 是"减数值"的改动，按项目惯例（`docs/交付标准_三位一体闭环.md` / 数值变更纪律）**属于需要主理人签字的项目**，且改完必须跑经济红线闸（`check_resource_redline.py` / pre_f5 第 11 道）确认不破 ±15%。

### 问题 2 · **死函数红线对 E-3 的约束**（执行纪律，不是设计问题）

门3 现状：**死函数 377 / 水位 396**（`.workbuddy/_dead_func_baseline.txt` 共 396 行；`pre_f5_check.py:963-982`、`:1111-1192`）。
