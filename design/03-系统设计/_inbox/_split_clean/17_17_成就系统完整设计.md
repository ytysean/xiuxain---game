17.1 整体设计原则与体系框架

17.1.1 核心设计原则
① 全维度无死角覆盖：五类成就（成长 / 经营 / 战斗 / 探索 / 社交）匹配全部玩法系统；日常有反馈、阶段有里程碑、长线有终极追求，避免任何玩法缺乏成就激励。
② 奖励零鸡肋：普通成就给实用刚需资源 / 道具；稀有 / 传说给永久增益 / 专属外观 / 限定功能，且上述奖励无其他获取渠道，保证成就价值的唯一性。
③ 阶梯式正反馈：新手期平均每 10 分钟解锁 1 项；中期按境界 / 建筑阶段递进；长线传说成就拉长留存，形成持续可预期的成长曲线。
④ 全系统深度联动：成就条件与奖励对齐丹药 / 装备 / 秘境 / 阵营 / NPC / 主线，不新增孤立数值，复用既有一切系统产出与实体。

17.3 奖励参数与 CSV Schema 规范

achievement_config.csv 为成就系统的权威数据表，由 engineering-lead 落地于 config/，本章仅定义 schema 与枚举，不承载具体 164 行（见 §17.4）。

列定义（11 列，逗号分隔，首行为表头）：
`achievement_id,ach_name,category,grade,condition_desc,condition_param,reward_type,reward_id,reward_num,point_num,unlock_tip`

| # | 字段 | 类型 / 枚举 | 说明 |
| --- | --- | --- | --- |
| 1 | achievement_id | 字符串 | 成就唯一 ID，全局唯一 |
| 2 | ach_name | 字符串 | 成就显示名 |
| 3 | category | `成长|经营|战斗|探索|社交` | 五类枚举 |
| 4 | grade | `普通|稀有|传说` | 三级枚举 |
| 5 | condition_desc | 字符串 | 条件人类可读描述 |
| 6 | condition_param | 整数 ≥0 | 条件数值参数（如达成数量 / 境界阶）|
| 7 | reward_type | `灵石|道具|装备|材料|代币|声望|永久增益|称号|传说称号|外观|buff|阵法|弟子|种子|功能` | 奖励类型枚举（原稿实际用到项的并集）|
| 8 | reward_id | 字符串 | 指向全局道具 / 称号 / 外观 / 功能 ID；本批次 [PL] 策略下不做跨表存在性校验（缺口见 §17.8）|
| 9 | reward_num | ≥0 数值（数量恒为整数；永久增益类为小数倍率，如 1.5） | 奖励数量 |
| 10 | point_num | `10|30|100` | 成就点数，对齐 §17.1.2 分级 |
| 11 | unlock_tip | 字符串 | 解锁时的提示文案 |

枚举约束：
- `category` ∈ {成长, 经营, 战斗, 探索, 社交}
- `grade` ∈ {普通, 稀有, 传说}
- `point_num` ∈ {10, 30, 100}
- `reward_type` ∈ {灵石, 道具, 装备, 材料, 代币, 声望, 永久增益, 称号, 传说称号, 外观, buff, 阵法, 弟子, 种子, 功能}
- `reward_num` 为 ≥0 数值（数量恒为整数；永久增益类为小数倍率，如 1.5）
- `condition_param` 为整数且 ≥ 0

> 说明：用户原稿「奖励参数全集」定义的几十个系统规则字段（buff_type / effect_scope / multiply_area / function_id / faction_id / is_hidden / is_server_notice / weight_rank 等）本批次暂不进表，留 §17 后续批次。

17.5 奖励 ID 缺口与 [PL] 策略

Phase0 审计发现：原稿 CSV 使用拼音通用名 ID（ju_qi_dan 等），而真实道具库采用数字 ID（pill_001 等）。抽样丹药全部缺失；称号 / 皮肤 / 功能权限等无对应承载表。

按用户决策采用「标 [PL] 出框架」策略：
- 能无歧义对应的少量项直接映射（如「灵石」→ 资源类灵石 ID）；
- 其余 reward_id 保留原值（拼音通用名）并标记 [PL]，待工程审计回填；
- 本批次 reward_id 字段不做跨表存在性校验，缺口由 §17.8 汇总。

> [PL] 标记含义：Placeholder（占位待回填），非最终可上线值。
