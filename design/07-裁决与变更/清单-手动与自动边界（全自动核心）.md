## 〇、核心设定的两条铁证

**1. `game_state.gd:3` 明文设计决策**

> 「移除手动「结算一日」「派遣历练」，改由登录时自动推演 elapsed 现实时间。」

**2. 核心循环**

```
系统自动产出（离线也在跑）  ──→  玩家做决策与裁决  ──→  影响后续产出效率
```

**玩家的价值是"把宗门配置得更好"，不是"手动重复操作"。**

## 四、由本清单直接推出的三条结论

### 4.1 「全自动」在实机曾经是停摆的（已修）

`推演至现在()` 只写在旧 UI 分支，而 `启用新UI := true` → **自动推演从未触发**。后果涵盖离线产出、弟子修炼突破、历练结算、日常周常刷新、宗门事件——即核心设定整体失效。已于本轮修复。

### 4.2 任务体系应锚定「自动产出 + 玩家决策」，而非「手动劳作」

详见 `DECISION-日常周常任务与全自动核心的对齐.md`。要点：
- **A 类（自动产出）7 个条件**，埋点**全部集中在 `推演一月()` 这 185 行内**，一次改完即可覆盖，不会漏埋、维护成本极低
- **B 类（玩家决策）约 13 个**，锚点在各决策函数
- **C 类（手动劳作）约 30 个**，与「移除手动操作」的设计决策直接冲突，应删除 / 改为自动 / 降级为成就里程碑
- 最自相矛盾：`collect_income`（「收取全宗资源产出」）—— 设计已移除手动结算，却设计了要求手动收取的日常任务

### 4.3 项目当前处于「旧 UI 已废弃但代码未清理」状态

死代码量可观：main.gd 整套旧 UI、30 关秘境链路、4 个离线模拟器、若干占位设置。这不阻塞玩法，但会持续误导后续判断——**本轮 S1-1 的误判（把不可达的旧 UI 链路当成"已完成"）就是直接代价**。

建议 S3 阶段按本清单 §三 逐项清理，并为 `main.gd` 旧 UI 代码加统一的 `@DEPRECATED-旧UI` 标记，避免再次误判。
