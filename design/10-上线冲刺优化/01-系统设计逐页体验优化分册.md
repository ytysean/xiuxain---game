## 0. 总览与方法论

### 0.1 上线标准基准（对标大厂修仙/放置品类）

本册以以下大厂手游为「上线标准」参照，逐页对照其体验水位：

- **《一念逍遥》**：竖屏修仙、社交宗门、自动修炼+手动经营双轨、强引导与新手指引、宗门任务日清节奏。
- **《剑与远征》**：AFK 放置、主界面信息密度与「一眼看懂下一步」、红点极简（仅主行动+可领）、英雄/装备养成深度。
- **《问道》/《少年西游记》类**：宗门经营、交易行、拍卖、阵营声望、成就殿堂、周常/月供节奏。

**一句话上线标准**：玩家在任意页面停留 ≤3 秒能回答「我在哪、该干嘛、有什么收益」；宗主（玩家）只做「不可替代的裁决」，弟子自动运转的细节用「回执」而非「操作」呈现；红点只承载待裁决队列；文案全修真化、零现代词。

### 0.2 贯穿全册的设计铁律（优先级高于任何单页方案）

1. **红点判据铁则（v3.1 §7）**：红点只承载「宗主待裁决队列」。弟子 AI 自决（穿装/服丹/突破/寻机缘）一律不亮红点；会自决的，不产生红点。改任何红点前先过此判据。
2. **不写死坐标（#010 §6.8）**：引导只绑语义（页面路由 / 控件 `Node.name`），禁硬编码 `(x,y)`。UI 仍频繁调整，坐标型引导比没有引导更糟。
3. **整页切换（IA 规范性约束）**：页面跳转 = 隐藏并重建内容容器，禁用同 ScrollContainer 内 `visible` 切 Tab；跨页 chrome（顶栏/底栏/目标条）不随页释放。
4. **灰锁置灰不隐藏（IA §5）**：受锁模块在导航上 `disabled + 🔒 + tooltip` 可见，禁隐藏（防「洞」与「不知有此功能」）。
5. **仿真铁律表达（FTE §2）**：「殿阁自动产出、弟子自动修炼突破、无需手动」是项目核心差异点，必须在首页与各功能首屏**直接表达**，而非藏在「?」里。
6. **文案修真化（FTE §5，裁决 D1）**：以任务书铁律#2 为准（禁现代词/禁干瘪数值如「X倍/X成」），作用域限「玩家可见文案」，不动字段名/CSV 列名/代码标识符/存档键。
7. **超重页分批渲染（#005 P1-2/P1-2b）**：长列表页（≥200 节点）一律数据/渲染分离、首批 ≤30、滚动近底续建；禁一次性全量建卡。

## 1. 全游戏级横切系统（先于任何单页）

### 1.1 信息架构与导航（IA）

**现状摘要**：5-Tab 分级导航（宗门/弟子/殿阁/历练/纪事）已落地，`bottom_tab_bar.gd` 实现健康；44 个二级页经 `ENTRY_SUB_PAGES` 单一路由注册，gating 走 `SystemUnlock` 单一来源（fail-open，实现干净）；灰锁置灰保留不隐藏（v5 已做）。首页 v5 为纯代码 UI（坐标手算），无嵌套 ScrollContainer，一页一滚。

**对照大厂差距**：
- 二级页**发现成本高**：入口仅能在首页 dock/「更多」面板出现，缺少「功能索引/舆图」式的按解锁状态浏览（仅 `宗门舆图`=page_atlas 做了索引页雏形）。大厂（如《一念逍遥》）在宗门页有清晰的宫格功能矩阵。
- **特例页「返回」语义不一致**：弟子详情/宗主详情走 CanvasLayer 复用实例，关闭恢复顶栏；但战斗场景（battle_scene）是独立全屏覆盖层，返回路径与其他不一致，易迷失。
- **引导锚点与 UI 坐标未解耦**：#010 明确「引导禁写坐标」，但当前首页 0 引导接入，未来接引导时若按坐标绑会漂移（见 §1.3）。

### 1.2 红点体系（参照红点系统规范 v3.1）

**现状摘要**：v3.1 已全量落地——判据铁则（只承载宗主待裁决）、5 Tab 角标（圆点/数字分档、右贴角、IGNORE 穿透）、`red_dot_manager` 缩进死区已修、父子聚合/弱信号隔离、配色对齐微信（#FA4F4F、无描边无发光、静止）。已删 `弟子_装备/弟子_突破/历练_结算/宗门_图录/快捷_库藏`，新增 `弟子_请示/历练_奇遇`。

- **第三待裁决队列游离（FTE C3）**：执法堂「待裁决违规」+「弟子请命」在 page_sect_manager 有 UI 但不在 `red_dot_init` ID 表，也不在传讯队列 ⇒ 有「宗主落笔」之事却无红点，违反判据铁则。

### 5.1 裁决 1 · 首日气泡补「高亮指向」——【结论：B（补高亮指向）】

**理由**
1. 大厂首日光圈高亮是留存标配（《一念逍遥》首日逐步高亮具体按钮）；纯居中文字气泡低于上线水位，正是 FTE 记录的产品落差。
2. 技术成本低：`main.gd::_入门指引_显示气泡` **已内置高亮框绘制分支**（`有目标` 时画「透明底 + 暗金 3px 边」框，`main.gd:3112-3126`），新 UI 现状只是刻意传 `目标==null`（`:3045`）⇒ 补锚点即复用之，非新建控件。
3. 抗漂移合规：#010 §6.8 允许「锚点型」（`Node.name` + 运行时 `get_global_rect()`，禁硬编码坐标）；现实现已是运行时取 rect，合规。
4. 附带收益：锚点钉 `name` 对 `ui_full_accept` 按名断言有复用价值，早钉早受益。

**施工规格（锚点型）**

### 5.2 裁决 2 · 老档该不该被补点亮新手目标链——【结论：B（只对新档激活）】

**理由**
1. **红点判据铁则（v3.1 §7.1）**：红点 = 宗主待裁决队列，**不是进度提醒**。新手目标链是「30 分钟开局教学」，对老档即进度提醒 ⇒ 违反铁则，并触发铁律⑭「无待办却亮红点」。
2. **实证**：`main.gd:3934` 无条件 `激活新手目标链()`。老档 `newbie_active` 持久化为 false（`game_state.gd:25623` 默认 false），一进主界面即被点亮 → `新手_有红点()` 转 true（`:9897`）→ `宗门_宗务` 红点亮（`sect_home_page.gd:436`）、面板显「筹备中（0/7）」（`main.gd:3205`）。
3. **选项 A 不可行/更糟**：7 链中 `newbie_001/002/004` 为**事件型**（`recruit_count` / `realm_first_enter` / `event_first_trigger`），`_新手_条件满足` 对事件型恒返 false（`game_state.gd:9947`），**无法自动判定完成**；状态型仅 `newbie_005/006/007`。故老档会**卡在 newbie_001**（链式 `prev` 未完成不推进，`_新手_已解锁:9872-9877`），红点常亮、0/7 停滞 ⇒ 比不激活更糟。要救 A 须把事件型改状态判据（`recruit_count`→`弟子列表.size()≥1`、`event_first_trigger`→宗门纪事非空、`realm_first_enter`→秘境进度标志），改动面大且引入语义偏差，非上线冲刺该做。
