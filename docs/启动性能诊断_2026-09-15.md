# 太玄宗门录 · 启动性能诊断报告

实测时间：2026-09-15 ｜ 引擎：Godot 4.7.stable ｜ 方式：headless 分阶段插桩（同一台机器、两次复现）

---

## 一、结论先行

**启动慢 = 编辑器 F5 慢 与 玩家登录慢，是两件不同的事，根因不同。**

| | 编辑器 F5 慢 | 玩家登录慢 |
|---|---|---|
| 上一轮已修 | ✅ 已修（焦点 rescan 阻塞） | ❌ 未触及 |
| 根因 | 编辑器只在获得焦点时才 rescan + reimport，一次性堵住主线程 | **GDScript 每次冷启动全量重新编译 + 141 个顶层 preload 全量展开** |
| 额外成本 | `.godot/imported` 6059 个散文件 / 962 MB 的散文件 IO | 无（导出 PCK 后是单包索引） |
| 玩家是否要付 | 否 | **是，且是主要成本** |

上一轮改的 `import_resources_when_unfocused=true` 解决的是"切窗口假死/文件损坏"，
**对玩家登录速度零帮助**。

## 二、实测数据

### 对照组

| 场景 | 耗时 |
|---|---|
| 空项目（无 autoload、无资源）引擎 init 基线 | **429 ms** |
| 本项目完整启动到首页可点 | **52.9 s**（两次：52.052 s / 52.879 s） |

两次结果高度一致 ⇒ **不是磁盘缓存/IO 抖动，是稳定的 CPU 计算成本**。

### 分阶段（headless，无渲染、无纹理上传）

| 阶段 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| A 引擎 init + 20 个 Autoload 就绪 | **37.4 s** | 71% | 20 个 autoload 脚本及其 preload 依赖树全量编译 |
| B load main.tscn（141 个顶层 preload 展开） | **10.2 s** | 19% | game_ui.gd 的 65 个页面场景 + main.gd 的 29 个 |
| C instantiate main | 0 ms | — | 可忽略 |
| D main._ready | 56 ms | — | 可忽略 |
| E `_登录_进入`（game_ui 装配 + 读档） | 2.3 s | 4% | 业务逻辑，合理 |
| F 遍历 52 个二级页 | 2.4 s | 5% | 每个约 46 ms，合理 |

> 注：headless 无渲染，真机还要叠加纹理上传 GPU 的开销，移动端 CPU 弱 5–10 倍，
> **实际玩家冷启动大概率比 52.9 s 更慢**。

## 三、根因三条（都有数据支撑）

### 1. GDScript 每次冷启动全量重新编译（主因）

- 全项目 **202 个 .gd / 5.99 MB**，Godot 4 无 GDScript 字节码持久化 ⇒ **每次启动重新解析 + 编译全部脚本**。
- 单体过大：`game_state.gd` **1.37 MB / 29283 行**（记忆里记的 11489 行已是旧值，现已翻 2.5 倍）、
  `main.gd` 267 KB、`disciple.gd` 220 KB、`dynasty_system.gd` 192 KB。
- `ui/` 目录 83 个脚本共 2.18 MB，全部在启动期被展开编译。

### 2. 141 个顶层 preload，启动即全量展开依赖树

| 文件 | 顶层 preload 数 | 内容 |
|---|---|---|
| `ui/game_ui.gd` | **65**（函数内 0） | 20+ 个页面 `.tscn` |
| `game_state.gd` | 47 | 各子系统 `.gd` |
| `main.gd` | 29（const 8 + var 20） | 场景 + 脚本 |

顶层 `preload` 在**脚本解析期**就执行，不是用到才加载。
⇒ 玩家还没看到首页，20 多个页面的脚本和纹理已经被全部编译加载完。

### 3. 不是 IO 瓶颈（排除项）

- 两次运行耗时一致，排除 OS 文件缓存影响。
- 20 个 Autoload 中 **16 个根本没有 `_ready`**，只有 `Game` 做实际工作。
- `Game._ready` 读的 config CSV 全目录仅 **362 KB**，其中真正 `FileAccess.open` 的只有 2 处
  （`_载入文案表`、`_加载称号配置`）。
⇒ **成本在 CPU 编译，不在读文件**。单纯优化 CSV 没有收益。

## 四、附带发现：真机必现的 shader 错误

启动日志固定报：

```
SHADER ERROR: Using 'return' in the 'fragment' processor function is incorrect.
   [0] _取底板材质 (res://ui_theme.gd:1572)
   [1] _ready (res://ui_theme.gd:1495)
ERROR: Shader compilation failed.
```

GLSL 的 `fragment()` 函数内不允许 `return`。
**玩家每次启动都会触发**，底板材质失效。建议顺手修掉（`ui_theme.gd:1572` 附近，`return` 改成条件分支）。

## 五、解决方案（按性价比排序）

### P0 — 顶层 preload 懒化（收益最大，风险可控）

把 `game_ui.gd` 的 65 个顶层场景 preload 改为「路由表存路径，切页时再 `load()`」：

```gdscript
# 现状（解析期全量加载）
const PageShop = preload("res://ui/page_shop.tscn")

# 改为（首次点击才加载）
const PAGE_PATHS := {
    "shop": "res://ui/page_shop.tscn",
}
func _get_page(id: String) -> PackedScene:
    if not _cache.has(id):
        _cache[id] = load(PAGE_PATHS[id])
    return _cache[id]
```

- 预期：B 阶段 10.2 s → 1–2 s
- 风险：低。不改数据、不改存档、不改战斗逻辑；`instantiate` 只有 1 处（`page = scene.instantiate()`），改造面集中。
- 配合：首屏保留首页 + 顶/底栏的 preload，其余全懒化。

### P1 — `game_state.gd` 的 47 个 const preload 改按需工厂

- 预期：A 阶段 37.4 s 可显著下降（这是依赖树展开的主体）
- 风险：中。这些是各子系统的 `preload`，改成 `Game` 内部的懒加载工厂需逐个核对调用点。

### P1 — 拆 `game_state.gd`（29283 行 / 1.37 MB 单体）

- 单体每改一次都要整体重编译，也是编译耗时的大头
- 风险：高。核心存档/战斗逻辑所在，动前必须 read-before-write + 全量 gate。建议放最后做。

### P2 — Autoload 瘦身

20 个 Autoload 里 16 个没有 `_ready`，纯被 preload 拖进来编译。
评估哪些可以降级为普通节点/懒加载单例。

### P2 — 纹理治理（已备脚本，未执行）

- `.workbuddy/auto_ui/govern_load_perf.py` 已写好，但**未跑 `--apply`**。
- 现状实测：143 张 `_36` 命名图标实际是 **2048×2048**（5–7 MB/张），
  但已设 `size_limit=256` 降采样，其中 132 张仍是 `compress/mode=0`（无损）。
- 期望：不是启动慢主因（已降采样），但对**包体体积**影响大，建议单独排期。

### 兜底 — 体感优化

启动先出标题屏 + 分帧加载，把白屏换成进度条。
但 **GDScript 编译是同步的、无法后台线程**，只能掩盖，不能消除。真正的提速必须靠 P0/P1。

# 补充第二轮：P0 实测 + 根因修正（2026-09-15）

## 一、P0「game_ui 65 个顶层 preload 惰性化」——实测无效，已回滚

改造方式：65 个 `const XxxScene: PackedScene = preload(...)` → 路径常量 + 首次打开时 `load()` + 缓存；
`_show_sub_page` 兼容 PackedScene / 路径字符串两种入参，保证 4 个测试脚本零改动。

### A/B 实测（同机同探针，各跑 2 次一致）

| 阶段 | 原版 | P0 改造版 | 差值 |
|---|---|---|---|
| A 引擎 init + 21 个 Autoload | 38.5 s | 38.5 s | 0 |
| B load main.tscn | 9.2 s | 4.3 s | **-4.9 s** |
| C + D | 0.07 s | 0.07 s | 0 |
| E _登录_进入（game_ui 装配 + 读档） | 2.4 s | 10.4 s | **+8.0 s** |
| **首页可点（TOTAL_TO_HOME）** | **50.1 s** | **53.4 s** | **+3.3 s** |
| F 遍历 52 个二级页 | 2.2 s | 36.5 s | **+34.3 s** |
| 全量（TOTAL_ALL_SUBS） | 52.3 s | 90.1 s | +37.8 s |

### 判定

- **净负收益**：B 省下的 4.9 s，被 E 阶段的 +8.0 s 吃掉还倒贴，首页可点反而慢 3.3 s。
- **更致命的副作用**：运行时逐个 `load()` 远比解析期批量 `preload()` 慢——同样 52 个页面
  2.2 s vs 36.5 s。等于把启动的一次性成本，转嫁成玩家操作中的 52 次约 0.7 s 卡顿。
- 结论：**在 Godot 4.7 上不要做「顶层 preload 惰性化」**。
- 改造版已存档 `.workbuddy/perf/game_ui_lazy_REJECTED.gd`；`ui/game_ui.gd` 已还原
  （65 个 preload、1311 行，0 残留），`pre_f5_check.py` EXIT=0。

## 二、根因修正：A 阶段 38.5 s 是**纯 GDScript 编译**

插桩实测（改完即还原）：

- `Game._ready` 内部耗时 **13 ms**
- `SectManager._ready` 内部耗时 **0 ms**

→ A 阶段 38.5 s 与 CSV / 配置 / 初始化逻辑**完全无关**（此前"改 CSV 无收益"的判断得到实证）。
真正的成本是 **21 个 Autoload 及其依赖树的 GDScript 编译**。

## 三、合成对照实验：两个关键倍率

用等体积（1.4 MB）合成代码，在干净空项目中以 autoload 方式编译：

| 变体 | 结构 | 耗时 |
|---|---|---|
| A_mono_cn | 1 个文件，中文标识符 | **1613 s** |
| C_mono_en | 1 个文件，英文标识符（结构同 A） | **586 s** |
| B_split20_cn | 20 个文件 × 70 KB，中文标识符 | 770 s |
| 空项目基线 | — | 0.09 s |

### 发现 1：中文标识符有约 **2.75 倍**编译惩罚

A 与 C 结构完全相同、字节数相同，唯一区别是标识符用中文还是英文。
中文版函数数更少却慢 2.75 倍 → Godot 4.7 的 GDScript 解析器处理非 ASCII 标识符存在显著开销。

### 发现 2：单文件过大有约 **2.1 倍**惩罚

同为 1.4 MB 中文代码，1 个文件 1613 s vs 20 个文件 770 s。

### 数据使用注意

合成代码是 4 万个极小函数，绝对数量级远大于真实代码（真实项目 6.28 MB / 202 文件只要 37 s），
**绝对数值不可直接外推**；但同结构下的**相对倍率（2.75x / 2.1x）具有参考价值**，
需在真实代码上复验后再据此决策。

## 三、进度条的真实度处理

实测 `load_threaded_get_status` 上报是**台阶式**的：

```
0.0 → 0.133 → 0.150（停约 6 s）→ 0.250 → 完成
```

直接喂给进度条会一顿一顿，所以：

- 显示值 `minf(真实值, 显示值 + delta × 0.45)` —— **平滑逼近，只慢不超前，不编造时间轴猜测**；
- 首批子资源未上报前走 `indeterminate` 滚动条，保证界面始终在动；
- 阶段文案每 1.6 s 轮播一条（灵气初聚 / 开辟山门 / 点检殿阁 / 召集门人 / 演算天机 / 山门将启）。

## 三、真机渲染验收（新增 `godot-ui-render-accept` 流程）

用一次性探针（窗口模式，非 headless）拍 720×1280 真机截图，**一次抓出三个真 bug**：

1. **`color_text_body_gold()` getter 不存在**（只有常量 `COLOR_TEXT_BODY_GOLD`）。
   致命之处：GDScript 运行时报错会**中断该函数后续所有语句**，于是 `_建底栏()` 里排在
   出错行之后的 `_pct = Label.new()` 全没执行 → `_pct` 保持 null → 之后每帧刷
   `Invalid assignment ... 'text' ... on a base object of type 'Nil'`。
   即「一个 getter 名写错」的症状是「半张页面消失 + 每帧报错」。
2. **`Image.load_from_file` 在 4.7 触发解析期报错**（`Invalid operands "Image" and "Error"`），
   **整个脚本加载失败**，截图都没拍成。改用 `FileAccess.open` + `Image.load_png_from_buffer`。
3. **替换 art 图后运行时仍渲染旧图**：编辑器 14:03 已把旧图导入成 ctex，14:54 覆盖源文件后
   非编辑器运行不会重新导入，直接吃旧 ctex。删 `.import` + `.ctex` + `.md5` 后编辑器于
   15:01 重建（ctex 1.09 MB → 2.0 MB，正好印证新图更细）。

同时补了一个真缺陷：`ResourceLoader.exists()` 为 false 时（新克隆 / CI / 刚换图）
整页会**静默退化成纯色底**，现改为降级 `FileAccess` 直读原图并 `push_warning`。

**几何一律像素分析核对**：按金色谓词逐行扫描归并成 band，读出主标题 design y 267–373
（居中 539）、进度条 y 1777–1779、填充 96→645（=62%，与设定一致）。
肉眼曾误判「进度条高了 150 px」，实为估错 —— 先量再改。
