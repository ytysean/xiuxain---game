# 裁决：日常/周常任务体系 vs「全自动」核心设定

> 日期：2026-08-31
> 触发：老大指出「整个游戏主打的就是全自动，第一次所有的行为逻辑都是全自动」，要求据此判定现有日常/周常任务是否必要
> 结论：**现有任务体系中约 2/3 的设计与本作核心设定冲突，应重构而非对接**
> 状态：⏳ 待老大拍板

---

## 一、先确认「全自动」在游戏里的真实实现（不是推测，有明文）

### 1.1 设计决策的明文记录

`game_state.gd:3`：

> 「移除手动「结算一日」「派遣历练」，改由登录时自动推演 elapsed 现实时间。」

**这是一条已执行的设计决策**：手动结算一日、手动派遣历练**都已被移除**。

### 1.2 自动推演实际产出什么（`推演一月()` L7510–7694）

登录时按流逝的现实时间自动推演，其中**无需玩家操作**自动发生的事件共 12 类：

| 行号 | 自动事件 | 类型 |
|---|---|---|
| L7550 | 弟子**突破**至新境界 | ET_BREAKTHROUGH |
| L7562 | 弟子**入司职**任职 | ET_APPOINT |
| L7566 | 修为精进（大幅） | ET_BREAKTHROUGH |
| L7568 | 修为精进，**升至 N 层** | ET_BREAKTHROUGH |
| L7573 | 触发**机缘/奇遇** | ET_QUEST |
| L7585 | 触发**随机事件** | 混合 |
| L7593 | 弟子**违反戒律，待宗主裁决** | ET_INFO |
| L7600 | 弟子**前来请示宗主** | ET_INFO |
| L7630 | **宗门事务待宗主批阅** | ET_INFO |
| L7632 | **宗门事件**发生 | ET_SECT |
| L7682 | **历练完成**（`ExpeditionSystem.检查并结算历练()`） | ET_LOOT |
| L7684 | 历练失败 | ET_INFO |

另有 `更新商队状态()`、`_宗门集市_日推进()`、`_推进差事系统()`、`ExpeditionSystem.每日重置()/每周重置()` 等自动推进。

### 1.3 玩家在这一切里做什么

不是"手动刷"，而是**决策与裁决**。`ui/page_sect_manager.gd` 的 13 个 Tab 就是玩家的全部动作域：

发展路线 / **殿阁任命** / **弟子任职** / **戒律裁决** / **弟子请示** / **宗主批阅** / 核心弟子 / 宗门科技 / 对外关系 / 议事会 / 商队管理 / 阵营声望

后端支撑 `sect_manager.gd`：`任命殿阁负责人()`(151)、`分配弟子任职()`(174)、`解除弟子任职()`(180)、`获取待裁决违规()`、`获取待回应请示()`、`获取待批阅事务()`。

### 1.4 核心循环（由此确立）

```
系统自动产出事件/产出 ──→ 玩家做决策与裁决 ──→ 影响后续产出效率
     （离线也在跑）         （配置宗门）        （正反馈）
```

**玩家的价值是"把宗门配置得更好"，不是"手动重复操作"。**

## 二、据此重新判定 50 个任务条件

判据不再是"系统是否存在"，而是：**这条任务要求的是「自动产出的结果」「玩家的决策」，还是「手动重复劳作」？**

### A 类 · 自动产出型（✅ 应保留 —— 与核心完全一致）

玩家不用做任何操作，任务随宗门运转自然完成。**这类才是本作任务体系应有的主体。**

| condition_type | 自动产出锚点 | 备注 |
|---|---|---|
| `breakthrough` | L7550 自动突破 | 周常 weekly_001 |
| `disciple_realm_3` / `disciple_realm_5` | L7568 自动升层 | 新手任务，是"状态"宜用查询而非计数 |
| `clear_stage` / `expedition` | L7682 历练自动结算 | 玩家只"派遣"，结算全自动 |
| `event_first_trigger` | L7585/L7632 事件自动发生 | — |
| `achievement_unlock` | 自动 | — |
| `milestone_unlock` | 自动 | — |
| `zongmen_battle` | 发起后**自动推演打完**（S1-3 已实现） | 玩家只做"编制 + 开战"决策 |

### B 类 · 玩家决策型（✅ 应保留 —— 就是核心玩法本身）

这些是**配置宗门的策略决策**，不是劳作，正是"全自动"设计留给玩家的动作。

| condition_type | 决策锚点 |
|---|---|
| `upgrade_building` | 升级殿阁（经营决策） |
| `refine_pill` / `forge_equipment` | 生产决策 |
| `learn_gongfa` / `deploy_zhenfa` / `upgrade_zhenfa` / `repair_zhenfa` | 配置决策 |
| `market_trade` | 交易决策 |
| `recruit_count` / `recruit_count_5` | 招募决策 |
| `add_friend` | 社交决策 |
| `disciple_interact` | 弟子互动（轻决策） |
| `handle_event` | **裁决/请示/批阅**（`page_sect_manager.gd` 三 Tab，实机可达 ✅） |
| `appoint_zhishi` | `sect_manager.gd:151 任命殿阁负责人()` / `:174 分配弟子任职()`（实机可达 ✅） |
| `elite_expedition` / `defeat_boss` / `defeat_elite` | 可由 A 类历练结算**派生**（按关卡类型/结果细分计数，不需独立系统） |

> **修正**：`handle_event` 与 `appoint_zhishi` 在上一轮普查中被误判为"不存在"——当时用关键词「待办」「任命」搜索没命中，实际实现叫「戒律裁决/弟子请示/宗主批阅」和「任命殿阁负责人/分配弟子任职」，**均在 `page_sect_manager.gd` 有实机入口**。

### C 类 · 手动劳作型（❌ 与核心冲突 —— 建议删除或改造）

这些要求玩家**手动重复操作**，正是 `game_state.gd:3` 那条设计决策要消灭的东西。

| condition_type | 冲突点 |
|---|---|
| **`collect_income` / `collect_daily_income`** | ⚠️ **最自相矛盾**：设计上已"移除手动结算一日"，却又设计"去手动收取产出"的日常任务（daily_001）和新手任务（newbie_003） |
| `collect_resource` | 手动采集 |
| `use_pill` | 手动用丹 |
| `feed_beast` / `train_beast` / `beast_battle` / `beast_evolve` | 手动喂养/训练/出战/进化 —— 灵兽应全自动成长 |
| `friend_interact` / `send_gift` / `friend_close` | 手动刷社交 |
| `explore_map` / `discover_ruins` | 手动探索 |
| `comprehend_gongfa` / `upgrade_gongfa` / `gongfa_max` | 手动刷功法 |
| `enhance_equipment` / `decompose_equipment` / `equip_set` | 手动刷装备 |
| `upgrade_skill` | 手动升级技能（且全项目无此系统） |
| `close_cultivation` | 手动闭关（按钮未接；且"安排闭关"更适合做成配置型） |
| `refine_treasure` | 祭炼法宝（无系统） |

## 三、结论与建议

### 3.1 结论

**1）大部分现有日常/周常任务的设计是错的。**

现有 43 条日常 + 24 条周常，照搬的是**手动操作型手游**的"每日劳作清单"模板。而本作已明确 `移除手动结算一日、手动派遣`，核心是"离线也在自动跑，玩家只做决策"。**任务设计没有跟上这条核心设定。**

**2）因此，问题不是"要不要补 33 个缺失系统"，而是"任务锚点该放在哪"。**

补系统（方案 A3，数月）是在错误的方向上投入：就算把"手动喂灵兽"做出来，它依然与全自动核心冲突。

**3）正确的方向：把任务锚点从「手动操作」迁移到「自动产出 + 玩家决策」。**

好消息是——**这两类需要的系统基本都在**，不需要大规模补功能。

### 3.2 建议：任务体系重构为「自动产出目标」

任务应从"要你做 N 次"改成"宗门今日/本周产出了 N"。

**日常示例（全部自动或单次决策，无劳作）**

| 任务 | 锚点 | 类型 |
|---|---|---|
| 今日弟子突破 N 次 | L7550 | A 自动 |
| 今日修为精进 N 次 | L7568 | A 自动 |
| 今日历练完成 N 次 | L7682 | A 自动 |
| 今日宗门事件发生 N 次 | L7632 | A 自动 |
| 今日裁决/批阅 N 件 | page_sect_manager | B 决策 |
| 今日升级殿阁 N 次 | page_building | B 决策 |
| 今日炼制丹药/装备 N 次 | page_pill_formula / blueprint | B 决策 |
| 今日达成 N 个成就 | 自动 | A 自动 |

**周常示例**

| 任务 | 锚点 |
|---|---|
| 本周累计突破 N 次 | A 自动 |
| 本周宗门战胜利 N 场 | A（S1-3 已实现） |
| 本周历练成功 N 次 | A 自动 |
| 本周达成 N 个成就/里程碑 | A 自动 |
| 本周殿阁累计升阶 N 次 | B 决策 |
| 本周招募弟子 N 名 | B 决策 |

### 3.3 关于 C 类任务的处置

| 处置 | 适用 | 说明 |
|---|---|---|
| **删除** | `collect_income` `collect_daily_income` `collect_resource` `use_pill` | 与核心直接冲突，**建议直接删** |
| **改为自动** | 灵兽喂养/训练、功法参悟、装备强化 | 若这些玩法未来要做，应设计成**自动执行**（如灵兽自动成长），而非每日手动点 |
| **降级为长期目标** | `gongfa_max` `zhenfa_max` `equip_set` `friend_close` | 不适合做日/周常，更适合放进**成就或里程碑**体系（长线追求） |

## 四、对 S1-2 的影响

| 项 | 原计划 | 按核心对齐后 |
|---|---|---|
| 范围 | 全量实现 50 个条件的埋点 | **只做 A 类（7）+ B 类（~13）≈ 20 个条件** |
| 是否需要补系统 | 需补 33 个 | **基本不需要** —— 现有系统已足够，只需迁移锚点 |
| 数据改动 | 补空条件 | **需重写任务表**：删 C 类、改造部分任务描述 |
| 埋点位置 | 分散在 50 处业务 | **A 类集中在 `推演一月()` 一处**（12 个事件点），B 类在各自决策函数 |
| 工时 | 3–4 天（且不可行） | **约 1.5–2 天** |
| 体验 | 大量任务永远完不成 | **每条任务都能随宗门运转自然达成** |

**A 类埋点的一大优势**：全部集中在 `推演一月()` L7510–7694 这 185 行内，一次改完即可覆盖"突破/升层/任命/机缘/事件/历练完成/历练失败"等全部自动产出，**维护成本极低、不会漏埋**。
