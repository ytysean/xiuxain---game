## 二、本轮深度学习成果（外网 + 国内社区 + 竞品，多源交叉验证）

### 2.1 权威规范层（**最高权重**）

| 来源 | 关键结论（原文/实证） | 对本项目的约束 |
|---|---|---|
| **网易游戏学院《窗口界面设计规范》**（《大巧不工》丛书） | 界面分四型：**窗口 / 全屏 / 伪窗口**。选择依据第一条：「**有主场景的游戏**（MMORPG / RPG / SLG / **养成**）→ 可在三种形式中随意选择」；窗口型适用「与场景有较强交互的游戏类型，如 MMORPG、SLG、**模拟经营**」 | ★★ **本项目＝模拟经营 → 规范推荐「窗口界面」**（有框体、透出场景），**而非零面板** |
| 同上 | **窗口禁忌（原文）**：「要**避免场景很亮、底板很暗的尴尬**（比如场景是白天，一打开界面是深色背景）」 | ★ **背景亮度与面板明度必须协调**（P0-5.1 踩过：亮青蓝山水衬暗卡片＝"贴纸感"） |
| 同上 | **窗口金字塔**：层级越高的窗口应越小，让玩家看清层级 | 面板必须**分层**存在，不是"能删就删" |
| *Game UI/UX Design Principles*（StraySpark） | **Minimum Viable HUD**：先留空，只加"能证明其常驻必要"的元素；**HUD 分区**：边角＝持久信息 / **中心＝瞬时信息** / 底部中央＝叙事 / 边缘＝次要 | 常驻数据该在**边缘**（顶栏/底部），**中心留给场景** |
| *Game UI UX*（skilldb） | 信息三级：Tier1 生存（常驻）/ Tier2 战术（可隐藏）/ **Tier3 策略（仅按需）**；「**绝不把 Tier3 放进常驻 HUD**」 | 司职明细/月产＝Tier3 → **只给概览数字 + 跳转**（P0-5 判据 1 已按此裁决） |

### 2.2 竞品实证层（**打脸"零面板"的最硬证据**）

| 竞品 | 首页真实做法 | 说明什么 |
|---|---|---|

| **寻道大千**（竖屏放置修仙 · 最直接对标） | 主界面**一分为二**：一半砍树（玩法/美术）+ 一半**装备与战力面板**；评价原文「一目了然，开门见山告诉玩家玩法是什么」 | **不是零面板**：数据面板是"开门见山"的载体 |

| **和平精英 UI 2.0** | 「**全景化动态背景**…仿佛每个界面都活起来了」 | 背景是主角 ✅（已落地） |
| **梦幻西游三维版** | 「**保证最大化的展示场景和角色本身**」＋「**半开放式界面**」：功能信息用**小界面**承载，其它空间继续展示主界面 | ★ **"小界面"（=适度面板）+ 大场景**，正是 P0-5.3 的路线 |

### 2.3 方法论层（国内社区 / B站博主）

| 来源 | 关键结论 |
|---|---|
| CSDN《UI界面设计：游戏操作逻辑与视觉平衡设计》 | 「**核心区域（如技能栏）适度紧凑，边缘与辅助区域则要大胆留白**」；两个必须避开的极端：**重视觉轻逻辑**（堆砌装饰致按钮难点、信息难读）／**重逻辑轻审美**（土气呆板、无沉浸感） |
| TrueSight（B站十年游戏 UI 设计师）《游戏UI布局设计避坑指南》 | 三大原则：**信息层级**（一眼抓住重点）／**易用性**（别让玩家"找瞎"）／**一致性**（统一风格营造沉浸） |
| Athena Productions《10 Game UI Mistakes》 | 三大高频错：**信息过载**（cognitive overload）／**层级不清**（weak visual hierarchy）／**设计语言不统一**（inconsistent design language）——**注意：没有一个错叫"面板太多"** |
| 站酷/语雀《明日方舟 UX 拆解》 | 「轻盈」的定义＝「**没有层层叠叠的界面堆积**」；手法＝**主体关联 + 转场动效**弱化跳转感、**互斥面板**收纳信息、**界面物理深度控制在 2–3 层** |

### 2.4 三条被我否掉的"流行但不适用"的说法

| 说法 | 为什么不能照抄 |
|---|---|
| "首页应该零面板" | 出自 **HUD**（战斗中）语境；主界面/主菜单的行业惯例恰恰相反 —— **边角承载持久信息**（StraySpark）。且主界面的数据面板 = 网易规范的「窗口型界面」 |
| "面板越少越好" | 面板的真正问题是**层级不清 / 数量爆炸 / 明度不协调**（Athena 三错），不是"存在本身"。**最强祖师玩家要的就是"综合面板"** |
| "把数据直接压在背景上" | 网易规范明令禁区：「避免场景很亮、底板很暗」；且本项目面板底 `alpha=255`（完全不透明）——**读字从来只靠面板自身，不靠背景压暗**（P0-5.3 实证） |

## 三、逐条核对：豆包 #005 的四处硬伤

### ① 「面板 4–5 → 0–1」＝方向性错误

- **规范层**：网易明列**模拟经营推荐窗口界面**（有框体、透出场景）。零面板属「全屏界面」——该规范同时警告全屏"**设计难度大、信息层级把控要求更高、层级深、易层级眩晕**…**MMO 不建议用**"。
- **竞品层**：§2.2 五款头部产品，**零面板者 0 款**。
- **物理层**：`panel_bg`/`card_bg` 中心 **alpha=255（完全不透明，实测 `rgba(28,41,47,255)`）**。面板是"在**任意背景照片**上都能读清字"的唯一保障。删掉它 = 复现 P0-5.2「背景压死」的反面错误（这次是"字读不清"）。

> **正确的收敛**：不是"删面板"，而是「**少而有秩序**」—— 减少**块数**（16 → 4 → 更少）、统一**明度/圆角/间距**、把**数据放边缘、场景留中心**。

### ② 「层层嵌套、视觉拥挤」的诊断**已过期**

豆包引用的现状依据是 `accept_shots_full/00_home.png`，但该诊断描述的是 **P0-5 之前**的首页（左右双列侧栏 + 各自独立圆角卡）。

P0-5.1/.2 已把「时令条 + 气象带 + 传讯栏 + 快照 4 卡 + 入口图标 ×5 + 快捷项 ×4」共 **16 个独立框**收为 **4 块**（情报面板 / 快照面板 / 入口带 / 快捷条）。P0-5.3 进一步让背景在 **11%–88% 全幅透出**。

⇒ 其"面板占据太多位置"的判断，**描述的已经不是现在的首页**。

### ③ 「复兴进度条 ████░░ 78% 浮在背景上」**不可行**

代码实证（`ui_theme.gd:61–84`）：

```
# ───────── H项：复兴进度→色彩饱和/明度派生 ─────────
# 复兴进度 0.0=破败（1品宗门）→ 1.0=辉煌（7品宗门）
func 设置复兴进度(门派等级): 复兴进度 = clamp((门派等级 - 1) / 6.0, 0.0, 1.0)
```

**它是一根"色彩派生旋钮"，不是可展示的进度值** —— 由 `Game.门派等级` 单向驱动，用于派生语义色/组件色的饱和与明度。

且顶栏已有「太玄宗 **Lv.1**」＝ 同一信息的另一种呈现 ⇒ 首页再放一条"复兴度 78%"＝**同一信息两处展示，撞 X12「一义一名一页」**。

### ④ 「签到 / 活动 / 邮件 → 浮动小按钮」**违规**

| 豆包写法 | 项目既有裁决 | 冲突 |
|---|---|---|
| 「活动」 | `UX设计总纲 §4.13`：活动**已修真化为「宗门时令」**（每日功课/周课/大典盛事），P0-5 v1.2 已全项目落地 | 命名回退 |
| 「签到」浮动按钮 | 首页「日供」已存在（快捷条），且**已由 P0-5 提升为顶部时令横幅** | 重复入口 |
| 「一键收取」式运营逻辑 | **项目铁律 #11**：宗主＝管理者，弟子任司职后**自动执行**，**禁止出现"一键收取/一键领取"类收菜逻辑** | 违反铁律 |

### 6.3 踩坑记录（本轮新增，血泪）

**`scrim` 高度必须止于顶栏边界，不能下探。** 首版写 `PANEL_H + 24`（≈211px），而首页「宗门中枢」面板顶边在 **168px** → scrim 把面板首行「大典盛事」压暗（真实渲染读图发现）。改为 `PANEL_H`（≈157px ≈ `TOPBAR_H` 156）后解决。
> **沉淀**：顶栏是**最后 add_child 的全局层**，其任何高亮/遮罩都会盖到 `offset_top = TOPBAR_H` 的内容区之上 —— 顶栏自带装饰**不得超过 `TOPBAR_H`**。
