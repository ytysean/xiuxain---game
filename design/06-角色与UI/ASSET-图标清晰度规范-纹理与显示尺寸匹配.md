# 图标清晰度规范 — 纹理分辨率与显示尺寸匹配

> 起因：主理人反馈「F5 实机图标都很模糊，上线后手机端更看不清」。
> 本文把「源图 → 导入纹理 → GPU 采样 → 屏幕物理像素」整条链路逐段量化，
> 给出可执行判据，并记录两轮落地改造 + 实测。**后续新增任何位图 UI 资产前必读。**

---

## 1. 概述

### 1.1 一句话结论

**图标发糊的主因不是「源图不够高清」，而是「导入纹理远大于显示尺寸」** ——
纹理被 GPU 线性过滤缩小时，每目标像素只采 4 个纹素，缩小倍数一旦超过 2 倍，
大量高频信息被丢弃并混叠。**源图越高清，缩小倍数越大，反而越糊。**

### 1.2 实测证据（同一图标、唯一变量 = 纹理分辨率）

实机渲染截图（720×1280 窗口），与「原图直接高质量重采样」的 PSNR 对比
（同一内容，故可横向比较；参考值：>30dB 肉眼难辨 / 25~30 细看有差 / <25 明显发糊）：

| 纹理长边 | 纹理 / 屏幕 | PSNR | 判定 |
|---|---|---|---|
| 1024px | 7.38 倍 | **14.5 dB** | 严重失真（改造前典型值） |
| 512px | 3.69 倍 | 19.5 dB | 明显偏糊 |
| **256px** | **1.85 倍** | **25.0 dB** | **接近肉眼难辨** |

> 从 7.38 倍降到 1.85 倍，**PSNR 提升 10.5 dB**，即误差降到约 1/11。

## 2. 核心规则

### 2.1 黄金判据

```
纹理长边 ≈ 该图标「最大显示物理像素」 × 2
```

- **低于 1 倍**（纹理小于显示）：GPU 放大 → 肉眼可见的软与块。
- **1 ~ 2 倍**：最佳区间，线性过滤采样覆盖完整，细节完整保留。
- **超过 3 倍**：混叠开始主导，出现边缘毛刺、细纹断裂、闪烁。
- **超过 6 倍**：无论源图多高清都等于白费 —— 采样根本读不到那么多纹素。

### 2.2 显示物理像素怎么算

```
显示物理像素 = 画布坐标 × (窗口宽 / 画布宽)
```

《太玄宗门录》当前配置（`project.godot`）：

| 场景 | 画布 | 窗口 | 缩放率 | 104 画布 px 图标实际显示 |
|---|---|---|---|---|
| 开发预览（F5，window_*_override=720/1280） | 1080×1920 | 720×1280 | **0.6667** | **69 px** |
| 实机打包（override 置 0 或删除） | 1080×1920 | 1080×1920 | 1.0 | 104 px |
| 高密度手机（1440 宽） | 1080×1920 | 1440×1920(等比放大) | 1.333 | 139 px |

### ★ 2.2.1 量纲陷阱：`UI_SCALE = 2.25`（2026-09-16 二轮实测踩到，必须牢记）

本项目 UI **存在两套长度单位**，混用会造成 **2.25 倍**的定档错误：

| 单位 | 出现位置 | 换算 |
|---|---|---|
| **480 设计单位** | `sect_home_page.gd` 等页面的坐标常量（如 `ENTRY_ICON_SIZE = 66.222`） | × `UITheme.UI_SCALE`(=2.25) = 真实画布单位 |
| **1080 真实画布单位** | `page_shop.gd` 等页面直接书写的尺寸（如 `icon_bg.custom_minimum_size = Vector2(120,120)`） | 即真实值 |

`sect_home_page.gd` 的 `_place()` 内部执行 `c.size = Vector2(w * s, h * s)`，
所以 **`ENTRY_ICON_SIZE = 66.222` 的真实落树尺寸是 `66.222 × 2.25 = 149`**
（该常量注释 `# 149 / 2.25` 即为佐证）。

> ⚠️ **定档时绝不能用页面常量的字面值**。若误按 66 计算得出 `size_limit=128`，
> 相对于真实显示 149 只有 **0.86 倍**，图标会由「缩小采样」变成「放大插值」——
> **比改造前更糊**。
>
> **唯一可靠做法：跑探针读运行时 `node.size`**（见 §4.3），它天然已含折算。

### 2.3 本项目取值（分族实测，2026-09-16）

判据：`size_limit = 2 × 该族「真实画布最大显示边长」`（实测值见 §7.1）。

| 族（`art/icons/` 下） | 实测最大显示 | 定 `size_limit` | 落实比值 | 依据 |
|---|---|---|---|---|
| `entry`（首页入口，双档 149 / 67.5） | **149.0** | **256**（保持） | 1.72 | 已最优；**不可降 128** |
| `building`（殿阁） | 216.0 | **512**（↑升） | 2.37 | 原 256 仅 1.19 倍，属欠采样 |
| `hd`（底栏 / Tab） | 99.0 ~ 117.0 | **256**（保持） | 2.19~2.59 | 可接受 |
| `shop` / `equipment` / `skill` | 104.0 | **208** | 2.00 | — |
| `resource` | 104.0 | **256**（保持） | 2.46 | 同族含 `_512` 命名成员，证据不足时不降 |
| `auction`（拍卖行） | 90.0 | **192** | 2.13 | — |
| `emoji` | 48.0 | **128** | 2.67 | 走 CPU LANCZOS 重采样，非 GPU 采样路径 |
| `disciple` / `array` | 未在实机出现 | **256**（保持） | — | 待实测后再定 |

| 其他目录 | `size_limit` | 说明 |
|---|---|---|
| 全屏背景（`art/backgrounds/`） | 0（不限） | 显示接近画布宽 1080，需保原尺寸 |
| 角色立绘（`art/characters/`） | 512（多数） | 见 §5.3 硬约束 |

### 2.4 配套开关

| 项 | 取值 | 理由 |
|---|---|---|
| `mipmaps/generate` | **false** | 缩小 ≤3 倍时线性过滤已准确；开 mipmap 反而偏软，且显存 +33%（**实测 mipmap 21.0 dB < 直接降到显示×2 的 25.5 dB**） |
| `compress/mode` | **0（Lossless）** | VRAM 块压缩（mode=2）会让细线/渐变/透明边出现块状伪影与色带 |
| `detect_3d/compress_to` | **0** | 置 1 会在纹理被 3D 使用时自动转 VRAM 压缩 —— 对 2D UI 属行为突变 |
| `process/fix_alpha_border` | true | 透明区 RGB 填边缘色，避免缩放时边缘发黑 |
| `process/premult_alpha` | false | 本批抠底图边缘干净；若后续出现"边缘发白/发暗"再开启 |

### 2.5 不要做的事

- **不要用「提高源图分辨率」解决发糊** —— 源图 1024 而纹理上限 512 时，多出的部分在导入阶段就被丢弃；纹理 512 而显示 69px 时，多出的部分在采样阶段被丢弃。
- **不要用 NEAREST 掩盖锯齿** —— 缩小场景下 NEAREST 会严重走样，但改成 LINEAR 只是把「硬锯齿」换成「软糊」，两者都不是解。**正解是让纹理尺寸落进 1~2 倍区间。**
- **不要一刀切给所有资产设同一个 `size_limit`** —— 判据是「显示尺寸的 2 倍」，实测各族显示尺寸相差 3 倍以上。
- **不要用页面常量的字面值定档** —— 见 §2.2.1 量纲陷阱。
- **不要凭 shader 承载的贴图判断比值** —— 底座 `art/ui/icon_base_atlas.png` 探针读作「2048 纹理 / 149 显示 = 13.7 倍」，实为**误报**：该图为图集（`cell=256`，8 列），shader 按格子采样，真实比值 256/149 = **1.72 倍**，本就合格。

## 4. 交互 / UI 要点

### 4.1 验收方式

图标的清晰度必须在**真实渲染**下验收，不能只看源图。判据：

1. `pre_f5_check.py` 全闸门 EXIT=0。
2. 实机截图放大后，图标边缘无毛刺、无摩尔纹，细节（纹路/篆字/描边）可辨。
3. 与「原图高质量重采样」的 PSNR ≥ 25 dB。

### 4.2 开发预览的固有偏差（需知悉）

`window/size/window_width_override=720` 使开发预览为 **0.6667 倍缩放**，
即**比实机糊约 1.5 倍**。这是当初为「2K 屏方便查看」而设。

- **不要**用 F5 窗口的观感直接判断实机画质；
- 需要精确判断时，临时把 override 改为 1080（或删除两行）后再看。

### 4.3 ★ 全族尺寸量测探针（新增，可复跑）

`tests/_probe_iconsize.gd` / `.tscn`

```bash
Godot_v4.7-stable_win64_console.exe --headless \
  --path "E:/Xiuxian/taixuanzongmenlu" res://tests/_probe_iconsize.tscn
# 产物：.scratch_backup/_probe_iconsize.txt
```

做法：载入 `main.tscn` → 登录探针账号 → 取 `新UI` → 遍历 `ENTRY_SUB_PAGES`
全部 52 个入口（走真实路由 id）逐个开页 → 读全树 `TextureRect` 的
**运行时 `node.size`** 与 `texture.get_size()` → 按 `resource_path` 归族取最大值。
覆盖 60 个页面，约 80 秒。

> **关键**：读运行时 `node.size`，不读源码常量 —— 天然规避 §2.2.1 的量纲坑，
> 也覆盖到布局计算（容器拉伸、`_place` 折算）后的真实值。

### 4.4 ★ 改动的安全验证法（改前改后探针比对）

因为存在「按纹理原生尺寸摆放」的写法会让 `size_limit` 变动**改变界面显示尺寸**，
任何 `size_limit` 批量改动后必须做一次比对：

1. 改动前跑一次探针，存档日志；
2. 改动后重跑，逐族比对「最大显示边长」；
3. **必须逐族完全一致** —— 一致即证明改动纯属纹理分辨率，零布局副作用。

> 2026-09-16 实测：7 个族 `最大显示` 全部一致，总判定 PASS。

## 5. 本次诊断的附带发现

### 5.1 `snap_2d_transforms_to_pixel` 在分数缩放下有害

`project.godot` 中 `2d/snap_2d_transforms_to_pixel=true` +
`snap_2d_vertices_to_pixel=true`。该两项是**为像素艺术游戏**准备的；
本项目在 0.6667 分数缩放下，吸附到整像素会让纹理采样点偏移，
表现为**轻微模糊 + 位移抖动**。建议对非像素艺术项目关闭（待裁决，未改动）。

### 5.2 坊市上架每次启动都随机（与设计约定不符）

`game_state.gd: 刷新坊市上架()` 使用 `randi_range(8, 12)` 决定上架数量 + `全部.shuffle()` 抽取。
⇒ **每次启动游戏，坊市货架都不同**（数量也变）。

这既与「坊市每日 08:00 固定刷新」的周期设计约定冲突，也让玩家无法规划。
建议改为「按真实日期（或累计游戏日）确定性抽样」，与 `XianyuShop.取每日特供()` 同一套做法。
（本次因影响面涉及经济节奏，未擅自改动，记此待裁决。）

### 5.3 立绘与背景仍为 VRAM 块压缩 —— 附硬约束数字

| 目录 | 源图数 | `compress/mode` | 现状 ctex 磁盘 | 若全改无损的显存（RGBA8 下界） |
|---|---|---|---|---|
| `art/characters/` | 1526 | **全部 2**（VRAM 压缩） | 272.7 MB | **⚠️ ~1915 MB** |
| `art/backgrounds/` | 9 | 8 个为 2 | 9.5 MB | 67 MB |
| `art/icons/` | 624 | 全部 0 ✓ | 37.2 MB | 113 MB |

> **硬约束**：把 `art/characters/` 全部改 Lossless 会让显存从约 240~480 MB
> 涨到 **~1.9 GB**，手机端不可承受。**这不是取舍问题。**
>
> **正解是两步走**：
> 1. 先按实测显示尺寸砍 `size_limit`（像素数可降 4~7 倍）；
> 2. 再改 Lossless 消除色带。
> 两步相抵后显存与现状持平或略降，同时色带消失。
>
> 第二轮实测的相关数据（供第一步定档参考）：
> - `art/characters/beasts`：显示 **104**，纹理 512 ⇒ **4.92 倍**，可降 `size_limit` 至 208；
> - `art/characters/masters`：显示 **2806**，纹理 1216 ⇒ **0.43 倍**（被放大 2.3 倍）。
>   这是**真正的模糊源**（立绘大图欠采样），但源图仅 1216 ⇒ 单纯调 `size_limit` 无法解决，
>   需重出高分辨率立绘，或降低该页的放大倍数；
> - `art/backgrounds/home_bg_season_*.png`：显示 486，纹理 1920 ⇒ **3.95 倍**（全屏渐变，色带风险叠加）；
> - `art/backgrounds/home_bg_sect_a.png`：显示 1921.5，纹理 1920 ⇒ **1.00 倍** ✓ 已完美。

### 7.2 ★ 两条头像资产来源（极易误判）

- **宗主头像** = `art/characters/masters_circle/*.png`（598~732 方图，**不是** `masters/` 下的 832×1216 全身立绘）。
  ⚠️ `masters/` 与 `masters_circle/` 存在**同名文件**，而 `.godot/imported/` 的 ctex 名只含 basename ⇒
  用 basename 去 glob 找 ctex 会**串扰**（会把全身立绘的 832×1216 误报成头像纹理）。
  **正解：读 `.import` 的 `dest_files` 字段（含 hash）定位 ctex。**
- **弟子头像** = `disciple.gd 取头像路径()` → `取立绘路径("halfbody")`
  → `弟子立绘/depth/depth_{类型}_{性别}_halfbody[.png|_elite.png|_top.png]`，
  再由 `page_disciple.gd` 用 `AtlasTexture` 取**中间正方形** + `avatar_circle_mask.gdshader` 裁圆。
  ⚠️ **不是** `disciples/头像/avatar_*.png` —— 那是旧界面 `main.gd` 的路径，`启用新UI=true` 后根本不构建。

### 7.3 ★★ 核心判据修正：mipmap 的收益取决于「缩小倍率」

前两轮的结论「mipmap 不如直接降 `size_limit`」**只对单一显示档位成立**。头像实测推翻了它的普适性：

| 档位 | 显示 | 缩小倍率 | 无 mipmap | 有 mipmap | **mipmap 净效应** |
|---|---|---|---|---|---|
| 弟子列表卡 | 112.5 | 2.28× | 27.32 | **35.43** | **+8.11 dB** |
| 宗主顶栏 | 117 | 4.4× | 33.59 | **35.82** | **+2.22 dB** |
| 宗主弹窗网格 | 252 | 2.03× | **41.81** | 38.47 | **−3.34 dB** |
| 宗主弹窗预览 | 270 | 1.9× | **43.31** | 39.06 | **−4.25 dB** |

**规律**：
- 缩小 **≥ 2.3×** ⇒ 开 mipmap（GPU 取 LOD1，采样比落到 ~1.1×，消混叠）
- 缩小 **≈ 2×** ⇒ **保持 LINEAR**（mipmap 会让 LOD1 被放大插值，反而更糊）

**⇒ 同一张纹理的不同显示档位，需要不同的 filter，不能全局一刀切。**

### 7.4 mipmap 生效的必要条件（最易漏）

`mipmaps/generate=true` **只是生成 mip 链**；能否被采样还取决于 `CanvasItem.texture_filter`：

- Godot 2D 默认 `Linear`（**不含 mipmap**）
- 必须显式设 `TEXTURE_FILTER_LINEAR_WITH_MIPMAPS` 才会用 mip 链

本项目 `project.godot` 未设 `default_texture_filter`（取默认 Linear）⇒
必须在**每个显示点**各自显式赋值（见 §7.5）。

### 7.10 三条裁决的落实（2026-09-16 四轮）

#### 裁决 1：弟子头像改「裁切区取头部」—— 已拍板方案 A 并落地

**现状几何**：弟子 `halfbody` 立绘源图是 **512×512 / 1024×1024 正方形**，
而 `page_disciple.gd:591` 写的是 `Rect2(0, (h-w)*0.5, w, w)` —— 当 `h == w` 时
结果就是 `Rect2(0, 0, w, w)`，**等于零裁切**。所以弟子头像 = 整张胸像压进 112.5px 框，
脸只剩约 **26~33 px**，这正是与宗主头像（脸特写）观感差距的来源。

**★ 现成数据**：`depth/avatar/crop_report.csv` 是当年用 **OpenCV DNN SSD** 跑的人脸检测报告，
含 36 条脸中心坐标。统计后得出一条**高度一致的规律**：

| 维度 | 实测范围 | 均值 |
|---|---|---|
| 脸中心 X / 图宽 | 0.496 ~ 0.506 | **≈ 0.500** |
| 脸中心 Y / 图高 | 0.313 ~ 0.340 | **≈ 0.325** |

⇒ **不需要逐张调裁切坐标**（原担心的风险不存在），一条公式覆盖全部（含 `_elite`/`_top`
变体，用比例自适应）：

```gdscript
var w: float = float(tex_res.get_width())
var h: float = float(tex_res.get_height())
var s: float = w * 0.50              # 裁切边长 = 宽 × 0.50
var cx: float = w * 0.50
var cy: float = h * 0.325            # 脸中心纵向比例（36 条 dnn_ssd 检测统计得出）
var x0: float = clampf(cx - s * 0.5, 0.0, w - s)
var y0: float = clampf(cy - s * 0.5, 0.0, h - s)
at.region = Rect2(x0, y0, s, s)
```

**样本结论**（`accept_shots_full/P_弟子头像裁切方案_样本.png`）：

| 方案 | 脸显示像素 | 构图判定 |
|---|---|---|
| 现状（零裁切） | 26 ~ 33 px | 胸像，脸过小 |
| **方案A `s=0.50W`** | **53 ~ 67 px** | **与宗主头像锚点基本一致 —— 推荐** |
| 方案B `s=0.45W` | 59 ~ 74 px | 更近，但 `bao_男` 的**冠顶被圆边切掉** ⇒ 不推荐 |

**★ 配套必改项（易漏）**：裁切后实际使用区域只有 `0.50 × 512 = 256 px`。
若 `size_limit` 仍是上一轮降到的 **256**，裁切区将只剩 128 px：

| 目标屏 | 显示物理像素 | 采样比（lim=256） | 判定 |
|---|---|---|---|
| 1080p | 112.5 | 1.14× | 勉强（无抗锯齿余量） |
| 1440p | 150 | **0.85×** | **欠采样 ⇒ 反而糊** |

⇒ **采纳裁切方案时，`depth/*_halfbody*` 的 `size_limit` 需同步恢复到 512**
（24 张，显存 +18 MB）。

> **2026-09-16 已落地**：`ui/page_disciple.gd:590` 已改用公式化裁切区；
> `art/characters/disciples/弟子立绘/depth/` 下 24 张 `_halfbody*.png.import`
> 已把 `process/size_limit=256` 恢复为 `512`；pre_f5_check.py 总判定 PASS。
