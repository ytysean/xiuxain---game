# 《太玄宗门录》正魔大战 P0 实现规格 · 代码现状对齐版

> 上游设计：`design/08-功能提案/22-正魔大战板块_设计评审与优化方案.md`（PROP_22）。
> 本文是 PROP_22 的 **P0 层落地规格**，一切表述以 **2026-09-03 实际代码现状** 为准；凡 PROP_22 与代码冲突处，本文以代码为准并显式标注。
> 决策前提（已锁定）：① 实现范围 = **P0 最小可玩**；② PROP_22 的 `[PLACEHOLDER]` 数值 = **按建议默认直接填**。

## 1. 概述

### 1.1 P0 目标
让「正魔对抗」从**纯文案设定**变成**可被战斗与经济系统真实消费的机制**，且不引入完整立场（stance）体系、不碰战斗红线、不升存档版本。

P0 交付三件事：
1. **数据一致性收口** —— 让三张 `faction_*.csv` 互相可 join，并首次纳入校验覆盖。
2. **非对称阵营克制** —— 战斗结算中正道/魔道互殴产生真实数值差异。
3. **阵营战役 → 战功闭环** —— 打阵营专属战役产出 `战功`，可在 S32 战功商店消费。

### 1.2 与 PROP_22 的关系
| PROP_22 条目 | 本规格处理 |
|---|---|
| P0-1 数据一致性 | **扩大范围**（代码现状比 PROP_22 描述的更糟，见 §2） |
| P0-2 非对称克制矩阵「替换对称 +10%」 | **改为新建**（对称 +10% 在代码中不存在，见 §2.3） |
| P0-3 战功商店入口 | **收窄为增量**（S32 已接通四类宗门战 → 战功，见 §2.4） |
| P1 / P2 / P3 | 本轮不实现，仅在 CSV 中预置列位 |

## 2. 代码现状核实（P0 的真实起点）

> 本节全部结论均由 grep / 校验器实跑核实，是本规格与 PROP_22 的差异来源。

### 2.1 真相①：三张 faction 表处于「三套口径并存」状态

| 表 | 阵营键形态 | 阵营集合 | 校验状态 | 活跃 `.gd` 消费方 |
|---|---|---|---|---|
| `config/faction_base.csv` | `faction_id` = `fz_*` 英文码 | 5 个，**含 `fz_danqi` 丹器师公会，缺远古遗泽** | ✅ 识别并校验（25 行） | ❌ **无任何活跃 .gd 读取** |
| `config/faction_quests.csv` | `faction` = 中文名 | 5 个，**含远古遗泽，无丹器师公会** | ❌ **未识别-跳过** | ✅ `game_state.gd:2173` |
| `config/faction_shop.csv` | `faction` = 中文名 | 同上 | ❌ **未识别-跳过** | ✅ `game_state.gd:2182` |
| `faction_system.gd` | `FACTION_LIST` 中文名 | 5 个，含远古遗泽 | — | ✅ 运行时权威 |

**根因**：`validate_all.py` / `csv_validator.gd` 中 `faction_shop` 的 `required_fields` 是 §11.26 设计的**新表结构**（`shop_id/faction_id/item_grade/price_lingjing/price_token/limit_daily/limit_weekly`），而 `config/faction_shop.csv` 是**老表结构**（`item_id/faction/item_type/price/description`）。表头不匹配 → `identify_table()` 返回 `None` → 整表跳过。`faction_quests` 更是**在校验规则里完全不存在**。

> 校验报告实证（`config/validate_report.txt`）：
> ```
> ## faction_quests.csv  [未识别-跳过]
> ## faction_shop.csv  [未识别-跳过]
> ```
> 两张**被运行时真实使用**的表，长期零校验覆盖 —— 这是数据漂移的根因，也是 P0-1 必须补的第一个洞。

### 2.2 真相②：声望等级存在两套互斥标尺

| 来源 | 等级序列 | 阈值 |
|---|---|---|
| `faction_system.gd`（运行时权威） | 冷淡 / 中立 / 友善 / 尊敬 / 崇敬 | 0 / 100 / 500 / 2000 / 5000 |
| `faction_base.csv` | 中立 / 友善 / 尊敬 / 崇敬 / **崇拜** | 0 / 1000 / 3000 / 8000 / 20000 |

`faction_quests.csv` / `faction_shop.csv` 的 `unlock_reputation` 列填的是**等级名**（中立/友善/尊敬/崇敬），与 `faction_system.gd` 对齐；`faction_base.csv` 的「崇拜」档是**孤儿等级**，运行时 `get_reputation_level()` 永远不会返回它。

**裁决**：运行时以 `faction_system.gd` 为唯一真源（因 `阵营声望` 是持久字段，改标尺即破存档）；`faction_base.csv` 向其对齐。

### 2.3 真相③：PROP_22 P0-2 的「对称 +10% 阵营克制」在代码中不存在

- `faction_base.csv` 的 `global_buff_1` / `global_buff_2` 两列**填的是中文描述文本**（如「正道弟子好感」「煞气抗性」），不是数值。
- 这两列**仅被 `csv_validator.gd` 当必填字段校验**，全项目无任何战斗逻辑读取。
- 全项目 grep `阵营克制` / `阵营加成` / `faction_buff` / `global_buff_1` → **零命中于战斗链路**。

**结论**：P0-2 不是「替换」而是**新建**。这反而降低了风险：新建可以完全落在 `zongmen_battle.gd`（非红线文件），不需要改动任何既有数值。

### 2.4 真相④：S32 已完成 P0-3 的一半

S32（宣战周期化 + 战场功勋）已落地：
- 货币 `战功` + `战功道具库存`（存档/读档/`new_game()` 三处对称）。
- 四类宗门战 → 战功：`宗门攻防战 60 / 秘境争夺战 50 / 妖兽围剿战 40 / 阵营围剿战 35`；败 8；硬战 ×1.5。
- 战功商店 `config/battle_merit_shop.csv`（11 件 4 类）+ `兑换战功商品()`。

**故 P0-3 收窄为**：新建 `faction_conflict.csv` 承载**正/魔对等的阵营专属战役**，走已有 `发起宗门战` 引擎，复用已有 `加战功()`。零新货币、零新商店。

### 2.5 真相⑤：`阵营任务进度` 以 `quest_id` 为持久键

`game_state.gd:2165` `var 阵营任务进度: Dictionary = {}`，键 = `quest_id`。

**故任何 `quest_id` 前缀重命名都会孤立旧档进度**（不崩溃 —— `_加载阵营任务配置()` 会为缺失键补 `{"进度":0,"已领取":false}` —— 但玩家已完成进度静默丢失）。

**裁决**：若执行前缀重命名，必须同步写**旧键迁移映射**（读档后把旧键值搬到新键并 `erase` 旧键），且迁移逻辑需幂等。

### 2.6 真相⑥：`faction_name` 是第三处漂移；`旧阵营映射` 无关本案

补充核实（2026-09-03 二轮）：

| 项 | 结论 |
|---|---|
| `faction_base.csv` 的 `上古妖兽族群` | 与 `FACTION_LIST` 的 `上古妖兽` **不一致** → 第三处漂移（前两处为 `faction_id` 口径、声望标尺） |
| `game_state.gd:2095` `旧阵营映射` | 仅为旧 4 阵营名（正道联盟/魔道势力/散修联盟/皇室官方）→ 新 5 阵营的**向后兼容别名表**，非独立键体系，**与本案无冲突，不改** |
| `game_state.gd:2084-2086` | 自带 `阵营列表` / `声望等级` / `声望阈值` 三个 const，与 `faction_system.gd` **完全一致** |

> ⇒ 「运行时权威标尺 = 冷淡/中立/友善/尊敬/崇敬 @ 0/100/500/2000/5000」有 **两处独立佐证**（`faction_system.gd` + `game_state.gd`），`faction_base.csv` 确认为**唯一孤儿**。§2.2 的裁决成立。

### 2.7 真相⑦：让两表进校验会立刻踩到 KeyError 雷

- `identify_table()` 逻辑为 `all(c in header for c in required_fields)` 取最长匹配 ⇒ **增列不破识别，缺列才跳过**（印证 §2.1 根因）。
- `validate_all.py:699-710` 的 faction_shop 跨表校验直接取 `r["item_grade"]` 与 `r["shop_id"]`，**老表两列均不存在**。当前不崩溃仅因该表「未识别」使 `rows_of()` 返回空。
- ⇒ **一旦 faction_shop 被识别，该段立即 `KeyError` 崩溃**。S33-2 必须同步重写此段，不能只改 `required_fields`。
- 同理 `validate_all.py:689` 硬编码 `order = ["中立","友善","尊敬","崇敬","崇拜"]`，改 `faction_base` 为「冷淡」档后 `order.index("冷淡")` 抛 `ValueError`，必须同步改。

## 5. 玩家阵营立场的 P0 轻量判定

P0 **不引入显式 stance 字段**（那是 P1-1 的双面声望范畴），改用**声望差判定**：

```
玩家立场 = 正道声望 - 魔道声望 > T1_LEAN  → "正道"
         = 魔道声望 - 正道声望 > T1_LEAN  → "魔道"
         = 其他                          → "中立"
```
- `T1_LEAN` = **500**（对齐 `faction_system.gd` 的「友善」阈值，非 §4.2 的 T1=1000 —— 后者是 P1 立场固化阈值，两者不同层）。
- 优点：零新增持久字段、零存档风险、复用既有 `阵营声望` 字典。
- 局限：立场随声望浮动、不可锁定 —— 这正是 P1 引入独立 stance 的动因，P0 阶段可接受。
