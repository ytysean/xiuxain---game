## 一、为什么必须先看这一节：三处反直觉的实证结论

本轮开工前做了代码与资产实证审计，推翻了三条常见假设。后续所有规范围绕这三条展开。

### 1.1 现状不是"没有设计规范"，而是"有大量设计文档但代码不执行"

`design/06-角色与UI/` 下已存在 **35 份** UI 相关规范文档（`UI设计令牌v1.0.md`、`太玄UI主题规范.md`、`首页UI布局规格.md`、`完整UX设计规范.md` …），但同语义常量在各文档与代码之间数值互相冲突：

| 来源 | GRID | MARGIN | TOPBAR_H | 口径 |
|---|---|---|---|---|
| `S1-UX验收规格.md` | 8 | 16 | 48 | 480 逻辑基准 |
| `S1-四页详细wireframe` | 8 | 16 | 48 | 480 逻辑基准 |
| `完整UX设计规范.md` | — | — | 56 | 480 逻辑基准 |
| `docs/UI样式审计与统一合并方案` | — | — | 108 | 混合口径 |
| **`ui_theme.gd`（实际代码）** | **12** | **24** | **158** | 见 1.2（混用） |

> **结论**：问题从来不是"缺规范"，是缺**可执行的「文档↔代码」一致性校验**。因此 P0-0 的产物不是新规范，而是一台**扫描器**——把规范变成每次提交都能跑的红线断言。

### 1.2 `ui_theme.gd` 内部存在两套单位口径混用（待裁决，见 §9）

| 类别 | 常量 | 是否需 ×UI_SCALE(2.25) | 证据 |
|---|---|---|---|
| **480 逻辑基准**（待换算） | `GRID=12` `GRID_SM=6` `MARGIN=24` `PAD_PANEL=24` `SIZE_SM/MD/LG/XL` `BTN_H_*` `FONT_*` | 是 | `ui_theme.gd:483-484` 函数内 `int(round(x * UI_SCALE))` |
| **1080 viewport 终值**（已换算） | `TAB_H=180` `TOPBAR_H=158` `OVERVIEW_H=180` `CORE_GRID_H=360` | 否 | `ui_theme.gd:156` 自证「80逻辑单位 × 2.25」 |

**后果**：不同开发者按不同口径理解同一批常量，导致间距/尺寸在不同页面上系统性错位——这是"参差不齐"的深层技术根源。

> **因此 `GRID_SM=6→8`、`TOPBAR_H=158→160` 两处改动暂缓**，须待 P0-0 口径报告产出后统一定夺（详见 §9 待裁决项 R1）。

### 1.3 材质资产缺失导致样式全线退化，这是"色块感"的直接物理原因

`ui_theme.gd` 早已预留贴图通道，但资产未到位，全部退化成 `StyleBoxFlat`：

- `ui_theme.gd:454`：`# 缺失则退化为 StyleBoxFlat（panel 基色 + 严格 1px 暗金描边）`
- `ui_theme.gd:801`：`# 加载面板暗纹贴图；缺失返 null（make_panel_stylebox 退化为 StyleBoxFlat）`
- `ui_theme.gd:461 / 596`：`StyleBoxTexture.new()` 通道已存在
- 但 `art/ui/` 下只有 `building_scenes/`、`master_detail/` 场景图与图标，**零 9-patch 底图**

> **结论**：填充 StyleBoxTexture 的资产是 P0 能否达到"手游质感"的物质前提。**贴图不到位，Token 定得再漂亮也只是"更整齐的色块"。**

### 2.2 工程原则（不可协商）

1. **样式单一真源**：一切视觉常量经 `ui_theme.gd`，业务页禁止出现裸 `Color(...)` 字面量与魔法数字。
2. **组件拼装**：页面由组件拼装，禁止裸写 `StyleBoxFlat`。
3. **结构层与纹理层分离**（见 §3.1）。
4. **复兴度派生优先**：Token 是函数而非常量（见 §4.3）。
5. **性能红线优先于视觉华丽**（见 §6）。

## 三、UI 材质资产规范

### 3.1 关键技术决策：结构层与纹理层必须分离

Godot 的 `StyleBoxTexture` **只拉伸、不平铺**。若把玉纹/纸纹画进 9-patch，卡片从 256px 拉伸到 1000px 时纹理将被放大约 4 倍而糊掉。故资产分两类：

| 类 | 内容 | 实现 | 说明 |
|---|---|---|---|
| **A 类 · 9-patch 结构层** | 渐变底 + 双描边 + 顶部高光 + 四角角饰 | `StyleBoxTexture` + `texture_margin_*` | 内部**零强纹理**（仅渐变与描边），拉伸无损 |
| **B 类 · tile 纹理层** | 玉纹 / 纸纹 / 云纹肌理 | 128×128 无缝 PNG + `TextureRect` tile 平铺 | 叠于结构层下方，**不拉伸只平铺** |

**★ 三层明度梯度（2026-09-13 修正，务必遵守）**
`panel #162024` < `row #1C262C` < `card #1F2B31`（取三者**下端**色比较）。
原 `card_bg` 下端为 `#182226`，与 `panel_bg` 下端 `#162024` 几乎同色，卡片贴面板时**下缘被吃掉**。
规定：**任何"浮在上层的容器"，其最暗处也必须比下层容器最暗处亮 Δ≥4/255**，否则层级不成立。

**九宫格边距取值依据**：`圆角 12 + 角饰 24~36 + 描边 2`，且**全部取 4 的倍数**（契合 `UI_SCALE = 9/4` 的整数映射要求）。

### 3.2.1 `card_bg` 角饰选型记录（4 轮迭代，2026-09-13）

`card_bg` 是小尺寸、高频复现元素（弟子卡 / 物品卡 / 列表行），角饰若不当会成为全屏视觉噪音。
经 4 轮候选实测（探针脚本 `.workbuddy/probe_card_orn.py`，产出 `.workbuddy/orn_candidates{,2,3,4}.png`）收敛：

| 轮次 | 候选 | 淘汰原因 |
|---|---|---|
| v1 | 正弦波云纹（原方案） | L≈22px 下退化为**抖动的线**，不可辨识为纹样 |
| v1 | 双线阶梯回纹（与 panel 同族） | 直线方钩在卡片尺度下像"电路板角"，过于机械 |
| v1–v2 | 双卷云勾（螺旋） | 两卷间距 <0.1L 时像"对望的钩子"；拉开到 0.42L 后仍像"两个逗号" |
| v2 | 双弧云角 + 宝珠 | 宝珠抢眼，整体像"毛毛虫" |
| v3 | 直角 + 宝珠 | 像"图钉" |
| **v4 ✔** | **内框弧角** | **采用** —— 与描边同构的 1/4 圆角内框线 + 两端渐隐，克制、干净，1× 下不抢戏、7× 下有"玉牌内框"层次 |

**关键设计判断（供后续资产复用）**：
1. **小尺寸元素（≤256px 源图）不做复杂纹样**。螺旋/宝珠等细节在 `L < 30px` 时一律糊成噪点，"少即是多"。
2. **角饰应与「描边」同构**（平行、同色系、更细更淡），而非另起一套形态语言 —— 同构产生层次，异构产生拼贴感。
3. **「无角饰」也是合格选项**（v3 候选 0）。角饰的价值是"点缀"而非"信息"，若形态拿不准，宁可留白。
4. **选型必须看 1× 真实尺寸**。预览板 7× 特写会放大设计差异，但玩家看到的是 1×；本轮探针专门输出 1× 并排排，避免被放大图误导。

### 3.2.2 `card_bg` 形态选型记录（第二轮 · 形态候选 9 套，2026-09-13）

第一轮（§3.2.1）只换了**角饰纹样**，收敛到内框弧角。但该结论有个盲点：**内框弧角在 1× 下几乎不可见**，
且"角饰"这条路换不出形态差异。故第二轮改问更根本的问题 —— **卡片长什么样**，
覆盖三个维度共 9 套候选（探针 `.workbuddy/probe_card_form.py`，产出 `.workbuddy/card_form_candidates.png`）：

| 维度 | 候选 | 结论 |
|---|---|---|
| 轮廓 | H 直角硬朗(r=2) / I 大圆角(r=22) / C 斜切八角(cut=18) | 未采用。C 最具国风辨识度，但**需 UI 侧留切角空间**，属布局耦合，无真实消费方前不出资产（避免死资产） |
| 结构 | **D 框中框** / E 上下端金扣 / **F 左侧书脊** | **D → 主卡**；**F → 列表行**；E 观感偏"在卡片里划两条线"，淘汰 |
| 装饰 | A 内框弧角(基准) / B 净版 / **G 右上角三角标** | **G → 状态角标**（独立资产）；A/B 保留为"无结构件"备选 |

**★ 新确认的 9-patch 安全规则（本轮实测，可直接复用）**：
1. 落在**上/下区**(`y<margin` 或 `y>H-margin`) 的装饰只被**水平**拉伸 ⇒ **横向贯通的细线/色带，竖向厚度守恒**。
2. 落在**左/右区**(`x<margin` 或 `x>W-margin`) 的装饰只被**垂直**拉伸 ⇒ **竖向贯通的细条，横向厚度守恒**。
3. 由 1+2 推论：**「完整内框线」在 9-patch 下是安全的** —— 圆角全在角区（不拉伸），
   上下直段只水平拉伸、左右直段只垂直拉伸（纯色线只变长不变粗）。故 D 候选成立。
4. **「四角切角」同样安全** —— 斜边全在角区，边区仍是直边。
5. **角饰(ornament) 与结构件(struct) 是两类东西**：角饰只影响四角、1× 下几乎不可见；
   结构件贯穿整条边/整个轮廓，1× 下清晰可辨，决定的是"形态"而非"点缀"。
   生成器已据此把参数隔离为 `orn_*` 与 `st_*` 两组键。

**★ 状态角标为什么单独出图**：它是**状态**而非**卡的形**，随状态变化而非随卡尺寸拉伸。
若画进 `card_bg` 就无法按状态关闭 —— 故做成独立小图 `corner_tab.png`，由 UI 层按需显隐。

## 四、Token 架构

### 4.1 三层结构

```
第一层  Primitive（原始色卡）── 整层可替换 = 将来换肤只动此层
        └ 见 §2.1 色表，禁止业务代码直接引用

第二层  Semantic（语义色 · 函数）
        └ func 表面(复兴度: float) -> Color
          func 描边(复兴度: float) -> Color
          func 点缀(复兴度: float) -> Color
          ...（背景 / 表面 / 强调 / 成功 / 危险 / 禁用 / 描边 / 分隔）

第三层  Component（组件绑定）
        └ 组件只绑 Semantic，永不直接引用 Primitive
```

### 4.2 为什么必须现在做

将 Token 从"常量"改为"函数"是**结构性变更**。若等 64 页全部绑定常量后再改造，代价是 64 页返工。

### 4.3 复兴度派生（差异化王牌）

复兴度 `r ∈ [0, 1]`（衰败 → 鼎盛）：

| Semantic | r=0（衰败） | r=1（鼎盛） | 视觉语义 |
|---|---|---|---|
| 表面 | `#162024` | `#1E2C32` | 宗门由晦暗转明润 |
| 描边 | `#6E5726` | `#C9A656` | 描边由枯金转亮金 |
| 点缀占比 | 8% | 22% | 金色面积随复兴递增 |
| 点缀饱和度 | 0.35 | 1.0 | "宗门长出金来" |

> 竞品 UI 是静态的；本作随复兴进度"长出金来"，这是唯一有可能形成差异化优势的视觉通道，必须在架构期留口，事后改造代价极大。

### 4.4 栅格派生约束（替代初版提出的"4 的倍数"）

> **修订记录 2026-09-13**：初版曾提出"所有尺寸必须是 4 的倍数"（依据 `UI_SCALE = 9/4` 的整数映射要求）。
> P0-0 实证审计**否定**了该前提——实测 26 个 int 常量中 **480 逻辑基准 = 0 个，1080 终值 = 20 个**，
> 即常量值已不再参与 ×UI_SCALE 换算，本身即整数像素 ⇒ **4 的倍数约束失去技术必要性**。
> 本节改为更正确的**栅格派生约束**。此修订保留在案，避免后续误用初版结论。

**规则**：布局尺寸应为 `GRID(12)` 的整数倍或半倍。

| 常量 | 值 | 倍数 | 判定 |
|---|---|---|---|
| `GRID` / `MARGIN` / `PAD_PANEL` / `SIZE_*` / `BTN_H_*` / `TAB_H` / `OVERVIEW_H` / `CORE_GRID_H` / `RADIUS_BUTTON` | 12/24/72~360/6 | 整数或半倍 | ✅ |
| **`TOPBAR_H`** | **158** | 13.17× | ❌ 非栅格派生 → 建议 **156**（13×GRID） |
| **`RADIUS_PANEL`** | **8** | 0.67× | ❌ 非栅格派生 → 建议 **12**（1×GRID） |

**豁免项（已确认，不可"修正"）**：
- `FONT_*` — 字形由 FreeType 亚像素渲染，天然容忍非整数；硬套倍数会把可用字号砍到少数几档，牺牲排版精度与阅读层级。
- `BACK_BTN_SIZE=40` — 触控目标遵循 ≥44px 独立标准，不从栅格派生。
- `BORDER_W=1` — 描边宽度属装饰量。

## 五、组件库规范

### 5.1 优先级（按出现频次，非通用性）

本作 64 页中列表与数值占约八成，故按频次排序：

## 六、性能红线（不可协商）

1. **禁止在 `_process` / `_draw` / 页面刷新逻辑中 `new StyleBoxFlat`**。`StyleBox` 是 Resource，可跨节点共享——必须**预创建为静态单例注册表**，节点只引用。64 页 × 数十 style 若每次重建，将造成 GC 抖动与显存泄漏，手机端直接掉帧。
2. UI 贴图统一 Lossless + `size_limit=0` + 关 mipmap（见 §3.5）。
3. **禁止实时模糊做玻璃层**——手机 GPU 带宽杀手。层次感一律由"渐变 + 描边 + 明度差"实现。
4. 9-patch 拉升区保持纯净渐变，禁止内含随机纹理（见 §3.1）。
